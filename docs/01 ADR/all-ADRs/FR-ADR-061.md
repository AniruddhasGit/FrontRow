## Context

`SRC-002 §4.9` puts movie posters in S3. `§10.6.3` — which survives in effect even though the section
around it is withdrawn (`§E E-2`) — says download posters once, store them in S3, serve our own URLs,
and **do not hotlink**.

`SRC-003 OPEN-TMDB-01` reverses the direction: the admin uploads posters instead of a job downloading
them. The storage rule is unchanged; the arrival path is new and unspecified.

Two things need deciding. How the file gets from the admin's browser into S3, given `§7.3` forbids
local file writes on the container. And how it gets to a customer's browser, given the no-hotlink
rule and the absence of a CDN.

## Decision

**Upload: a multipart POST to the API, streamed to S3, never touching the container's disk.**

The admin's browser posts the file to an admin endpoint. The API validates it and streams it to S3
using the SDK. **Nothing is written to local disk at any point** (`§7.3`) — the body is streamed
through, and a bounded size limit means it never has to be buffered whole in memory either.

**Validation, in this order, before anything reaches S3:**

- **Content length ≤ 2 MB.** Rejected at the header before the body is read.
- **Content type is `image/jpeg`, `image/png` or `image/webp`.**
- **The declared type matches the file's actual leading bytes.** A `.png` extension on a file whose
  content is something else is the standard upload attack, and the declared content type is
  client-supplied.
- **The image decodes**, and its dimensions are within a sane range. A file that claims to be an image
  and cannot be decoded is served to every customer as a broken image.

**The stored object key is generated by the server**, `posters/{movie_id}/{random}.{ext}` — never the
client's filename. A client-supplied filename is a path traversal and an overwrite in one field.

**The bucket is private. No public-read, no bucket policy granting anonymous access.**

**Serving: the API returns a 302 redirect to a presigned GET URL**, valid for one hour. The movie row
holds the object key (`FR-ADR-021`) and the URL is minted at request time.

**Why a redirect rather than proxying the bytes.** Proxying every poster through the API spends the
API's memory and its single uvicorn worker's time (`FR-ADR-057`) on serving static files, on a
`t3.micro`. A redirect costs one small response and the browser fetches from S3 directly.

**Why presigned rather than a public bucket.** A public bucket is enumerable and is the standard way
an S3 bucket ends up serving something nobody intended. A presigned URL expires, and the redirect
endpoint is a place a check can live if `OPEN-ATTRIB-01` ever requires one.

**This is not hotlinking.** `§10.6.3` forbids serving a third party's URL from our pages. Every poster
URL points at our bucket and is minted by us.

**A one-hour expiry with browser caching.** The redirect response carries a short cache header so a
customer scrolling a listing does not re-request the redirect for every card, while the presigned URL
itself outlives any single page view.

**Locally, S3 is the real thing or nothing.** No local S3 stand-in is added — that would be a new
dependency under `§13.1` and MinIO is a container inside a constrained development environment. Local
development uses a real S3 bucket with the developer's own credentials, or runs without posters, which
is a supported state because the poster is nullable until publication (`FR-ADR-021`). **This is the
weakest part of this record** and it is stated plainly: local development does not fully exercise the
upload path without AWS credentials.

**Posters are never deleted** (`FR-ADR-012`). Replacing a movie's poster writes a new object and
updates the key. The old object stays, which costs a few kilobytes against a 5 GB allowance
(`§5.2.5`) and means an audit row's `before` value still resolves to a real image.

## Alternatives rejected

**Presigned PUT direct from the browser to S3.** The usual answer, and it is better for large files.
Rejected because it moves validation to the client: the API never sees the bytes, so the type check,
the magic-byte check and the decode check cannot happen before the object exists. At 2 MB there is
nothing to gain that offsets that.

**Public-read bucket with direct URLs.** Rejected above.

**Proxy the bytes through the API.** Rejected on memory and on the single worker.

**CloudFront in front of the bucket.** Rejected — outside `SRC-002 §4` and needs permission under
`§4.12`. It is the right answer at scale and is not needed at this one.

**Trust the client-declared content type.** Rejected: client-supplied.

**Use the uploaded filename as the object key.** Rejected: traversal and overwrite.

**MinIO locally.** Rejected under `§13.1`, with the consequence stated above rather than hidden.

**Generate thumbnails on upload.** Rejected under Art VII.6. Nobody asked, it needs an image library
in the runtime image against a 250 MB target, and a 2 MB poster served once and browser-cached is not
a problem yet.

## Consequences

**The task role needs `s3:PutObject` and `s3:GetObject` on `arn:aws:s3:::<bucket>/posters/*` and
nothing wider.** Part of the IAM specification owed under `§6.4.2`. The bucket, with public access
blocked, is a prep-queue item with a *needed by* stage of Phase 6.

**No NAT Gateway means the container reaches S3 over the public internet from a public subnet**
(`§5.4.4`). S3 is one of the outbound paths `FR-ADR-065` enumerates.

The 2 MB limit and the accepted formats are configuration, and the admin form states them before the
upload rather than after a rejection.

**If `OPEN-ATTRIB-01` closes in a direction that requires attribution**, the redirect endpoint is
where a provenance check would live and the movie row is where the field would go. Neither is built
speculatively (`FR-ADR-007`).

# E4 — Receipt and entry

This epic covers everything between "the money is taken" and "the customer is standing at the door".
It owns the booking reference — how it is generated, stored, formatted, and read back when a person
types it — the confirmation page that shows it, the receipt email that carries it, the machinery that
guarantees that email is attempted exactly once and never twice, and the manual human check at the
entrance. It does not own the confirm transaction or the money (lane E3), and it does not own the
customer's bookings list as a screen (lane E5); it owns the reference that appears in that list.

The one thing that will be got wrong: **the emailed receipt is not a notification.** It is the
customer's only proof of purchase and their only way into the hall (`SRC-003 OPEN-EMAIL-01`,
`OPEN-TICKET-01`), and there are no refunds (`SRC-003 OPEN-CANCEL-01`). A developer who implements
the send as "commit the booking, then call SES" has built a system where a process restart at the
wrong instant produces a customer who has paid and cannot get in, with nothing anywhere that knows a
receipt was owed. The send is durable before it is fast: a row in a transactional outbox committed
with the booking (`FR-ADR-031`), a claim row that makes a second send impossible (`FR-ADR-032`), and
a reference on screen that never depended on the email in the first place (`FR-ADR-048`). Two further
things get got wrong and are stated here once: **no QR code is generated anywhere** — `SRC-001
§5.3.3`'s "scannable ticket" is corrected by erratum `E-9` and `SRC-002 §8.5.1`'s QR code is withdrawn
by erratum `E-5` — and **the reference is designed to be read aloud by a customer and typed by a
person at a door**, which is the whole reason it looks the way it does.

## S4 — Product specifications

### `P-TKT-01` · Generate the booking reference · `RULED`
`[SRC: SRC-001 §5.3.3 · SRC-001 §E E-9 · SRC-003 OPEN-TICKET-01 · SRC-004 R-5 · FR-ADR-015]`
`[BRD: R-TKT-01 · R-TKT-04]`

**Behaviour.** Every confirmed booking is given one reference that belongs to it alone: eight
characters from a 26-character alphabet — seven drawn by a cryptographically secure random source,
then one check character — stored uppercase with no prefix and no separators, under a unique
constraint on the column. **The 8th character is a check character computed over the first 7, from
the same alphabet; its algorithm is recorded in the code that implements it** (`SRC-004 R-5`, which
rules that the check character exists and leaves its arithmetic to the build session).

**Who may do it.** Nobody. This is not a user action. The reference is generated by the server inside
the booking confirmation transaction (lane E3's confirm path) and there is no endpoint that mints one.
No role reaches this behaviour directly, so there is no router dependency to apply.

**Preconditions.**
- A booking row is being inserted inside an open transaction.
- The `booking.reference` column exists with a `UNIQUE` constraint on it.
- A cryptographically secure random source is available (Python's `secrets`, not `random`).

**Happy path.**
1. Draw 7 characters, each an independent uniform draw from the alphabet
   `23456789ACDEFHJKMNPQRTVWXY`, using a rejection-free method over the secure source, and append
   the check character computed over them.
2. Store those 8 characters, uppercase, on the booking row inside the same transaction that inserts
   the booking. The `FR-` prefix and the hyphen are **presentation only** and are never stored.
3. The `UNIQUE` constraint is the guard. If the insert violates it, discard the value, draw again, and
   retry — **bounded at five attempts in total**.
4. On the fifth failure the request fails with `INTERNAL_ERROR` rather than looping. A generator that
   cannot produce a free value in five draws is broken, and a loop hides that.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | The drawn reference collides with an existing row (attempts 1–4) | no response yet; the transaction retries internally. Nothing is returned to the client | nothing — the retry is invisible and the booking succeeds |
| 2 | Five consecutive collisions | 500 `INTERNAL_ERROR`, the transaction rolls back, the seats are not sold | "Something went wrong and your booking was not completed. No payment was taken. If you need help, quote `a1b2c3d4`." |
| 3 | The secure random source is unavailable at process start | the process fails to start (`FR-ADR-053`); no request is served | nothing — the container never becomes ready |

**Server-side validation.** The generated value is validated before insert: exactly 8 characters, every
one a member of the alphabet, uppercase, and the 8th equal to the check character of the first 7. The
database enforces the alphabet and the length as well (`ck_booking__reference_charset`); it cannot
verify the check character. A value failing that check is a programming defect and raises
rather than being corrected. There is no client input on this path, so there is nothing a customer can
send that reaches it.

**Worked example — the reference space, and the honest collision expectation.**

The alphabet has 26 characters. The length is 8, of which 7 are random — the check character adds
no space. The space is therefore:

```
26^7 = 8,031,810,176        (8.03 x 10^9)
```

The 100,000 figure below is a round number chosen to make the arithmetic legible. **It is not a
forecast** — this project has one venue of six halls totalling 960 seats
(`SRC-003 OPEN-SCALE-02`, `ASSUMED`), so the real count is far smaller.

With `n = 100,000` references already stored, the probability that one freshly drawn reference collides
is:

```
100,000 / 8,031,810,176 = 1.245 x 10^-5        (about 1 in 80,318)
```

The probability that **all five** attempts collide, which is the only case that fails a booking, is
that figure to the fifth power:

```
(1.245 x 10^-5)^5 = 3.0 x 10^-25
```

The expected number of colliding pairs anywhere in the first 100,000 references is `n^2 / 2N`:

```
100,000^2 / (2 x 8,031,810,176) = 0.62
```

Stated plainly: **the first collision is expected at about 126,700 references** — the `n` at which
`n^2 / 2N` reaches 1, `sqrt(2 x 8,031,810,176) = 126,742`. That is far more than one theatre will
issue (`SRC-004 R-5`). A collision is caught by the unique constraint rather than by trusting this
arithmetic, and it costs one extra insert. The arithmetic is not the guard; the constraint is.

**What the alphabet fixes and what it does not. Written down because the reference's only real
consumer is a person reading eight characters aloud at an entrance with no software in the path**
(`P-TKT-08`).

**Excluded, exactly as `SRC-003 OPEN-TICKET-01` asked** (*"no `0`/`O`, no `1`/`I`/`l`"*): `0`, `1`,
`I`, `L`, `O`, `U`; **and `Z`, `S`, `B`, `G` by `SRC-004 R-5`**, which removes one member of each visual
pair `2`/`Z`, `5`/`S`, `8`/`B`, `6`/`G` and keeps `2 5 8 6`. What that leaves is not unambiguous, and
the document may not imply that it is:

| Still inside the alphabet | Confusable | Where it bites |
|---|---|---|
| `C` `D` `E` `P` `T` `V` `3`; also `M`/`N` | by ear, read aloud or over a telephone | `P-TKT-08` step 1 and step 2 — no exclusion list fixes this half; a spoken alphabet is confusable at any size |

**The check character detects a mis-read; it does not correct one.** It catches every single-character
substitution and every adjacent transposition (`SRC-004 R-5`), so a value mis-read in either way is
not a well-formed reference and cannot be another booking's. `P-TKT-02` still refuses to guess. At the
door it helps nobody, because `P-TKT-08` has no software in the path to compute it.

**What the product does about that: nothing, deliberately, and the consequence is not symmetrical.**
`P-TKT-02` corrects nothing, and it is right not to — a system that guesses can admit the wrong
person. So a mis-read surfaces **online** as the flat 404 of `P-TKT-02` exception 2, which is
recoverable because the customer can look again; and **at the door as no failure at all**, because
`P-TKT-08` has nothing to compare the characters against.

**This is not `OPEN-SEATLABEL-01`'s defect, and the difference matters when the two are read
together.** Two stored references can never differ only in case or spacing: the value is generated
uppercase from a fixed alphabet, stored uppercase with no separators, and normalised with an
ASCII-only uppercase on the way back in (`P-TKT-02`). There is no collision half here. The exposure is
the same surface and the same deadline; the mechanism is not.

**The narrower alphabet and the check character were raised as `PROPOSED-REFCHAR-01` /
`OPEN-REFCHAR-01` and are ruled by `SRC-004 R-5` (2026-10-18), before the first booking.** The length
stays 8 and the display form `FR-XXXX-XXXX` is unchanged.

### `P-TKT-02` · Accept a reference typed by a person, and correct nothing · `RULED`
`[SRC: SRC-003 OPEN-TICKET-01 · SRC-003 OPEN-TICKET-02 · FR-ADR-015 · FR-ADR-058]`
`[BRD: R-TKT-04 · R-TKT-01]`

**Behaviour.** A reference supplied as input is normalised — uppercased, with whitespace, hyphens and
an optional leading `FR` removed — and then matched exactly. **Nothing is mapped, aliased or guessed.**
A reference that does not normalise to eight characters of the alphabet does not resolve, and the
answer is the same as for a reference that does not exist.

**Who may do it.** Any authenticated caller of `EP-TKT-01`, enforced by the authentication dependency
on the router. Guests get `AUTH_REQUIRED`. Ownership is enforced separately (`P-TKT-09`).

**Preconditions.**
- The caller is authenticated.
- The input is present in the path.

**Happy path.**
1. Strip all whitespace characters and all `-` characters from the input.
2. Uppercase the result using an ASCII-only uppercase, not a locale-aware one.
3. If the result begins with `FR` and is 10 characters long, remove the leading `FR`.
4. Assert the result is exactly 8 characters and every character is in
   `23456789ACDEFHJKMNPQRTVWXY`. If not, stop and return the not-found response (below).
5. Match the normalised value against `booking.reference` with an equality comparison. The stored value
   is already uppercase and unseparated, so this is a plain index lookup and never a `LIKE`, never a
   case-insensitive collation, and never a similarity search.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | No credentials | 401 `AUTH_REQUIRED` | "Sign in to see this booking." |
| 2 | The normalised value is not 8 characters of the alphabet — for example the customer typed `0` where the reference has `O`, or `1` where it has `I` | 404 `NOT_FOUND` | "No booking with that reference is on your account." |
| 3 | The value is well formed but no booking has it | 404 `NOT_FOUND` — **byte-identical to row 2** | as row 2 |
| 4 | The value is well formed and belongs to another customer | 404 `NOT_FOUND` — **byte-identical to row 2** | as row 2 |
| 5 | The raw input is longer than 64 characters | 404 `NOT_FOUND`, rejected before the database is touched | as row 2 |
| 6 | **The per-user lookup bucket is empty** — `RATE_LIMIT_LOOKUP_USER_PER_MIN`, 20 per minute | 429 `RATE_LIMITED` with `Retry-After: 3` | "Too many attempts. Try again in 3 seconds." |
| 7 | **The per-IP lookup bucket is empty** — `RATE_LIMIT_LOOKUP_IP_PER_MIN`, 60 per minute, which is what refuses first when several callers share one address | 429 `RATE_LIMITED` with `Retry-After: 1` | "Too many attempts. Try again in 1 second." |

**Rows 6 and 7 are two rows because two buckets guard this endpoint and the header carries whichever
one refused** (`FR-ADR-058`, `S7.20`). A single row publishing one figure would be unimplementable —
an engineer could not tell which bucket the number came from. The figures are **derived, never
typed**: `Retry-After = ceil(window_seconds / capacity)`, so `ceil(60 / 20) = 3` and
`ceil(60 / 60) = 1`. **Row 7's singular is load-bearing copy that ships, not a defensive branch** —
`S7.20` names this bucket as one of only four in the product that reach `Retry-After: 1`, and an
implementer writing `"{n} seconds"` unconditionally ships "1 seconds" on a live path.

**The row previously published "45 seconds", and 45 is derived from nothing.** It was neither
bucket's refill interval, neither one's capacity and neither one's window; it was a number. It is
recorded here rather than quietly replaced, because the class of defect — a capacity or a window
written into copy that wants a refill interval — is what `S7.20`'s derivation table exists to catch,
and `P-ACC-12` in the account section already published the correct 3 for the same buckets, so this
section was disagreeing with its own sibling.

Rows 2, 3 and 4 return the same status, the same code and the same message on purpose. A response that
distinguishes "no such reference" from "not yours" is an oracle that tells an attacker which guesses
were real, and this reference is the only thing that gets a person into a hall.

**Server-side validation.** `reference` path parameter: string, 1..64 characters, rejected at 65+
before any normalisation or query. After normalisation: exactly 8 characters, each in the alphabet.
Every failure produces the identical 404. There is no client-side normalisation that the server
trusts; the browser may format the input for display, and the server normalises again regardless.

**Worked example — normalisation.**

| Input, verbatim | Normalised | Result |
|---|---|---|
| `FR-ABCD-EFGH` | `ABCDEFGH` | resolves |
| `fr abcd efgh` | `ABCDEFGH` | resolves |
| `abcdefgh` | `ABCDEFGH` | resolves |
| `  FR-abcd-EFGH  ` | `ABCDEFGH` | resolves |
| `FR-0BCD-EFGH` (a zero typed for the letter `O`) | `0BCDEFGH` | **does not resolve.** `0` is not in the alphabet. It is **not** mapped to `O`, because a system that guesses can admit the wrong person |
| `FR-1BCD-EFGH` (a one typed for `I`) | `1BCDEFGH` | does not resolve, same reason |
| `FR-ABCD-EFG` | `ABCDEFG` | does not resolve — 7 characters |

### `P-TKT-03` · Show the reference on confirmation, immediately and independently of the email · `RULED`
`[SRC: SRC-003 OPEN-EMAIL-01 · SRC-001 §5.3.4 · SRC-001 §5.4.2 · FR-ADR-048]`
`[BRD: R-TKT-03]`

**Behaviour.** The moment a booking is confirmed the customer is shown the reference, the seats, the
hall, the showtime, the film and the amount paid, on a page that is durable and reachable again. The
page **never states that an email has been sent**, because at that moment it has not been: the send is
asynchronous through the outbox and the queue.

**Who may do it.** Any authenticated account, **for their own booking and no other** — enforced by the
authentication dependency plus the ownership rule on the router (`P-TKT-09`). **There is no admin
override**: an `admin` reaches this page for their own bookings on exactly the terms a `customer` does.
A guest cannot reach it, because a guest cannot book (`SRC-003 OPEN-BOOK-02`).

**Preconditions.**
- The booking row is committed with a reference (`P-TKT-01`).
- The outbox row for the receipt is committed in the same transaction (`P-TKT-04`).

**Happy path.**
1. The confirm response (lane E3) carries the reference. The interface navigates to
   `/bookings/{reference}`, **passing the confirm response itself in the client's navigation state.**
2. `SCR-TKT-01` renders the reference block, the booking facts, and — **only on this first render
   immediately after confirmation** — the sentence that a receipt is on its way to the account's email
   address.
3. On any later visit to the same URL the page renders the same booking facts and **no sentence about
   the email at all**. See the note below; this is deliberate.

**How the page knows which of the two it is: the navigation state, and nothing else.** The two success
states are distinguished by **the presence of the confirm response in the client's navigation state**
— what a router carries from one route to the next within a single client-side navigation. It is
present exactly once, on the navigation the confirm performed. The rule is:

```
confirm response present in navigation state   ->  first render:  the receipt sentence is shown
absent                                          ->  later visit:   no sentence about the email at all
```

- **A reload is a later visit.** A full page load starts a fresh navigation state, so the sentence is
  absent after `F5`, after a bookmark, after a pasted URL and after a return from the bookings list.
  **This is the behaviour, not an accident of it.**
- **No endpoint field distinguishes the two, and none is added.** `EP-TKT-01` returns the same body on
  every request and `P-TKT-09` refuses to widen it — the dispatch state is deliberately off the
  customer API. Adding a `first_view` or `just_confirmed` field would make the server responsible for
  remembering a client's history, and a second request would then have to change the answer.
- **The rejected alternatives, so the next reader does not re-litigate them.** Comparing `paid_at`
  against now with a threshold makes the sentence appear on a reload inside the threshold and vanish a
  second later, with the threshold itself unruled; branching on the HTTP referrer breaks when the
  referrer is stripped, and is not present on a client-side navigation at all. Navigation state is the
  only one of the three that is deterministic and that a reader can check by looking at the client.

**The consequence, stated rather than hidden.** A customer who reloads within seconds of confirming
**no longer sees the address their receipt is going to.** They lose that sentence permanently for that
booking; nothing brings it back. What covers them is what the page already shows in **both** states:
the booking reference, in the reference block, which is the customer's proof of purchase and their way
into the hall and never depended on the email (`FR-ADR-048`). The resend control is also present in
both states, and its `202` body names the address again (`EP-TKT-02`).

**No replacement copy is written for the later-visit state, and none may be.** What a customer is told
about their receipt outside the first render runs into `OPEN-EMAILFAIL-01`, which is **`OPEN`** and
reserved to the client (`FR-ADR-049`). This decision fixes only *which* of the two existing states
renders; it does not add a sentence to either, and it closes no part of that row. The judgment that no
`PROPOSED-` row is needed here is recorded in the lane notes with its reason.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | Not signed in | 401 `AUTH_REQUIRED` | "Sign in to see this booking." |
| 2 | The reference does not resolve for this account | 404 `NOT_FOUND` | "No booking with that reference is on your account." |
| 3 | The lookup fails for any unhandled reason | 500 `INTERNAL_ERROR` | "Something went wrong. Your booking is not affected. If you need help, quote `a1b2c3d4`." |
| 4 | Redis is unreachable, so the rate limiter fails closed | 503 `DEPENDENCY_UNAVAILABLE` | "This page is unavailable right now. Your booking is not affected." |

**Why the later visit says nothing about the email.** On the first render the sentence is true — the
outbox row is committed, so the job exists and cannot be lost. On a visit an hour later it may not be
true, because the send may have definitively failed, and `OPEN-EMAILFAIL-01` reserves what a customer
is told in that case (`FR-ADR-049`). **Saying nothing is not a policy; writing a replacement sentence
would be.** Omission is the strictly conservative option and it closes no question.

**Server-side validation.** No writable field on this specification. The reference path parameter is
validated by `P-TKT-02`.

**Worked example — rendering the booking facts.** Stored showtime instant `2026-08-21T13:45:00Z`;
`FR-ADR-018` requires storage in UTC and display in Asia/Kolkata, which is UTC+05:30. The rendered
time is **21 Aug 2026, 7:15 pm** — `S7.19`'s date-with-time form. **The zone is not printed on this
page**: rule 2 prints it only on the emailed receipt, which is read away from the site.

**The money inputs are the seeded ones**, so this example can be transcribed into a test and asserted
against a seeded database (`S1.5`). `P-XCT-30` seeds a base price of `24999` paise and a Premium
uplift of `1250` basis points; three Premium seats give, under `FR-ADR-038`:

```
per seat  = (24999 * (10000 + 1250) + 5000) // 10000
          = (24999 * 11250 + 5000) // 10000
          = (281,238,750 + 5000) // 10000
          =  281,243,750 // 10000
          =  28,124 paise                      exact quotient 28,123.875, so the +5000 rounds it up
total     = 28124 + 28124 + 28124 = 84,372 paise    the sum of already-rounded per-seat prices,
                                                     never a total that is itself rounded
rendered  = ₹843.72
```

The page renders the stored total; it never recomputes it (`FR-ADR-039`).

*(This example previously used a base of `25000` and an uplift of `1200`, giving `28000` each and
`₹840.00`. Both were wrong to leave: the uplift contradicted the seed's `1250`, so a test transcribed
from here would assert a number the seeded database does not produce — and `25000 x 11200` is
`280,000,000`, which divides by `10000` **exactly**, so the `+5000` rounding term did nothing and the
example demonstrated a rounding rule using inputs in which no rounding occurs. The seeded figures fix
both: they match the data and the rounding term actually fires.)*

### `P-TKT-04` · Enqueue the receipt through a transactional outbox · `RULED`
`[SRC: SRC-002 §8.5.1 · SRC-002 §E E-5 · SRC-002 §7.3 · SRC-003 OPEN-EMAIL-01 · SRC-003 OPEN-QUEUE-01 · FR-ADR-031 · FR-ADR-059 · FR-ADR-056 · FR-ADR-060 · FR-ADR-067]`
`[BRD: R-TKT-02]`

**Behaviour.** The receipt job is created by inserting a row into `outbox_message` **inside the
booking transaction**, immediately before commit. It commits with the booking or it does not exist.
A separate relay step sends it to the queue. There is no post-commit send with no record.

**This outbox is the whole product's queue, not this lane's.** The account lane's password-reset email
travels through the same table, the same relay and the same worker. A vocabulary with one member and a
payload fixed at the receipt's four keys **cannot represent that message**: it could not be enqueued at
all, it could not say which reset it is for, and `P-TKT-05`'s "delete a message whose `booking_id` does
not resolve to a confirmed booking" would have silently destroyed it if one somehow got in. That is not
a cosmetic gap. **A locked-out customer's only route back into their account runs through this table**,
on a product where an email address stays taken permanently and where nothing is ever deleted
(`FR-ADR-012`). The vocabulary is therefore stated here with both of its members, rather than left for
whoever writes the account lane to widen quietly.

**`topic` is a controlled vocabulary with exactly two members in v1**, and the payload shape is fixed
per topic. A row whose `topic` is not in this table is rejected at insert. A row whose payload key set
is not exactly the shape given for its topic is rejected at insert.

| `topic` | Payload keys — exactly these, and no others | Who inserts it |
|---|---|---|
| `receipt.send` | `booking_id`, `dispatch_seq`, `request_id`, `message_version` | lane E3's confirm transaction (`P-PAY-10` step 10 — the `outbox_message` insert; step 9 is the `receipt_dispatch` row it carries the `dispatch_seq` of) and `P-TKT-07`'s resend |
| `password_reset.send` | `user_id`, `reset_token_id`, `request_id`, `message_version` | the account lane, on a password-reset request |

**The reset token itself never travels in the queue.** The payload carries `reset_token_id` — the
identity of a row — and never the token value. A token is a credential, and a queue message is at rest
in a service the application does not own, is redelivered more than once, and is copied into a dead
letter queue that nothing prunes and nobody watches (`P-TKT-11`). The worker reads what it needs from
PostgreSQL. This is the same rule `FR-ADR-059` already imposes on customer data, and the same reason
`receipt.send` carries no email address, no seat list and no amount.

**Who may do it.** Nobody directly. The insert happens on lane E3's confirm path; the relay runs in
the API process immediately after commit and in the worker's receive loop. No role and no endpoint
reaches it.

**Preconditions.**
- `outbox_message` exists with `id`, `created_at`, `topic`, `payload` (`jsonb`), `status`
  (`pending` / `sent`), `sent_at`, `attempts`, `last_error`.
- `receipt_dispatch` exists, with the columns `P-TKT-05` gives it. **This specification creates its
  row for every booking the application confirms; `P-TKT-05` only ever transitions one.** The seed
  script is the one other writer and it writes the row `suppressed` — see the block below.
- `QUEUE_URL` is configured. In AWS it points at SQS; locally at ElasticMQ (`FR-ADR-059`).
- `QUEUE_SEND_TIMEOUT_MS` is configured. It bounds the fast-path send in step 3 below, and it is the
  only thing standing between an unreachable queue and a confirm response that never returns.

**Happy path.**
1. Inside the booking transaction, after the booking and its seats are inserted and the payment is
   captured, insert **two** rows:
   - the `receipt_dispatch` row for this booking, with `dispatch_seq = 1`, `status = 'pending'`,
     `attempts = 0` and every timestamp null. **This is the only place in the running application a
     `receipt_dispatch` row is created.** The worker's claim transitions an existing row and never
     inserts one (`P-TKT-05`). The seed script is the one writer outside the application and it writes
     `suppressed`, never `pending` — the block below;
   - one `outbox_message` row with `topic = 'receipt.send'`, `status = 'pending'`, `attempts = 0`, and
     a payload of exactly `booking_id`, `dispatch_seq` — the `1` just written — `request_id` and
     `message_version`. **No customer data travels in the payload** — no email address, no seat list,
     no amount (`FR-ADR-059`).

   The two rows commit with the booking or neither exists. **Creating the dispatch row here rather than
   in the worker is what makes `dispatch_seq` in the payload refer to something at the moment it is
   written**, and it is what lets `P-TKT-07`'s resend read a row while the worker is down — which is
   precisely the state a resend is most likely to arrive in.
2. Commit.
3. **Fast path, and it is bounded.** The same request now calls the queue's `send` **under
   `QUEUE_SEND_TIMEOUT_MS`**, and on success updates the row to `status = 'sent'`, `sent_at = now()`.
   This is what happens almost always. **A timeout is treated exactly as a failure** — step 4.
4. **Recovery path.** If step 3 fails, or the process dies before it, the row stays `pending`. Before
   each poll of the queue, the worker selects `pending` rows older than a short threshold with
   `SELECT ... FOR UPDATE SKIP LOCKED`, in a bounded batch, sends them and marks them `sent`. This runs
   on the worker's existing loop; **there is no scheduler and none may be added** (`SRC-003
   OPEN-PROC-01`).
5. `sent` rows are kept forever as the record that the receipt was dispatched (`FR-ADR-012`). Nothing
   prunes this table.

**Where the fast-path send sits in the confirm request, and what bounds it. Both halves are stated
because neither is inferable from the other and a developer has to guess both.**

**It is inside the request, and the confirm response is emitted after it.** Step 3 runs in the API
process, in the confirm request's own thread, after the commit — it is `E3 P-PAY-10` step 15, the last
of that specification's three post-commit steps — and **the response the customer is waiting for is
emitted after step 3 returns, whether it succeeded, failed or timed out.** The customer's wait
therefore includes the queue call. Nothing is emitted early and nothing is handed to a background task:
a background task is process-local state that a SIGTERM or a SIGKILL loses (`P-XCT-18`, `P-XCT-17`),
which is the failure the outbox exists to make impossible, and re-introducing it here to save a few
hundred milliseconds would trade a durability guarantee for latency.

**Because it is inside the request, it carries a timeout, and the timeout is the customer's worst
case.** `QUEUE_SEND_TIMEOUT_MS = 2000` (**`ASSUMED`** — no source states a figure). Worked through
against `P-PAY-10`'s own worked example, whose transaction takes about **1.56 seconds**: an unreachable
queue makes that confirm about **3.56 seconds** and then returns `201` normally, because the booking
is already committed and no outcome of step 3 can change it.

```
worst-case confirm = transaction (~1560 ms) + QUEUE_SEND_TIMEOUT_MS (2000 ms) ≈ 3.56 s
```

**The bound is the value, not a multiple of it.** The AWS SDK retries a failed API call by default,
and three attempts at a two-second timeout is a six-second hang that no reading of the variable's name
would predict. **SDK-level retry is disabled on this path**: the retry that matters is the relay in
step 4, which is the one that also survives the process dying, and a second attempt inside the request
buys nothing the relay does not already provide 30 seconds later.

**`QUEUE_SEND_TIMEOUT_MS` must stay well below `SHUTDOWN_DRAIN_TIMEOUT_SECONDS`** (20 s, `S7.9`), or a
SIGTERM arriving while a send is hung means the drain cannot finish and SIGKILL lands mid-request
(`P-XCT-17` exception 3). At 2000 ms it is a tenth of it. **This ordering cannot be checked at boot in
one place** — both values are read by the API — so it is checked in `S7.9` and stated here.

**No timeout at all is the worst available outcome and it is what the document said before this pass.**
An unreachable queue would hold the confirm response open until the load balancer's idle timeout or the
customer's browser gave up, so the customer who has paid would see a failed request against a booking
that is committed, seats that are sold, and a receipt that the relay was going to send anyway. The
outbox exists so that the queue being down costs nothing; an unbounded call inside the request hands
that cost straight back to the customer.

**The `suppressed` state, and why the seed writes one rather than no row at all.**

`suppressed` is a first-class member of `receipt_dispatch.status`, alongside `pending`, `sending`,
`sent` and `failed`. It means, exactly: **no send was ever attempted, none will be attempted
automatically, and that is a fact about the row rather than a failure of anything.** A `suppressed`
row carries `dispatch_seq = 1`, `attempts = 0`, and `claimed_at`, `sent_at`, `ses_message_id` and
`last_error` all null.

**Only the seed script writes it, and the application never does.** `P-XCT-30` and `P-XCT-32` create
demonstration bookings whose accounts all sit on the reserved `SEED_EMAIL_DOMAIN`, a domain that
cannot resolve (`FR-ADR-067`), so the seed enqueues no receipt job for them: in the SES sandbox those
sends are refused, and outside it they would be hard bounces charged against the sending identity's
reputation, which can suspend the SES account and take the real receipt path down with it
(`FR-ADR-060`). **E8 owns the seed's half of this and this row does not restate it**; what is owned
here is the state, its meaning, and the fact that no application path produces it.

Why the three alternatives were rejected, stated so the next reader does not re-litigate them:

| Rejected | Why |
|---|---|
| **No row at all** | It contradicts `P-TKT-07`'s precondition that a confirmed booking always has a dispatch row, and lands all **11,003** seeded bookings on the branch `P-TKT-05`'s claim table calls unreachable (`P-XCT-30` derives the figure from its own occupancy rule; this row previously said "roughly sixty", which was never computed from anything and was wrong by more than two orders of magnitude). **A specification with a reachable unreachable branch is the defect, not the data.** |
| **`pending`** | It makes the row look like work the queue has not got to yet. A worker's relay, or an operator draining the outbox by hand, would be right to try to send it — into a domain that cannot receive it. |
| **`sent`** | It is a false record of an email nobody sent, in a table whose entire job is to be the record of what was sent. |

**`suppressed` is not an answer to `OPEN-EMAILFAIL-01` and must never be read as one.** That row is
about a send that was attempted and definitively failed, with money already taken from a real
customer. A `suppressed` row records that no send was attempted, for a booking no real customer made.
The two are different facts and the open row stays open (`FR-ADR-049`).

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | The outbox insert fails | the whole booking transaction rolls back: no booking, no seats sold, no payment recorded | the confirm screen's failure copy (lane E3). Nothing about a receipt, because no booking exists |
| 2 | The queue send in step 3 fails, **or does not answer within `QUEUE_SEND_TIMEOUT_MS`** | **nothing about it is returned to the customer.** The failure is logged at `ERROR` with the `request_id`; the row stays `pending` and the worker relays it. The confirm response is emitted at the point it always is — after step 3 — carrying its ordinary `201`, at most `QUEUE_SEND_TIMEOUT_MS` later than it would have been | nothing. The confirmation page renders normally |
| 3 | The API process dies between commit and step 3 | as row 2 | nothing |
| 4 | The worker is down | receipts are delayed, not lost. They go out when it restarts | nothing on the site |
| 5 | The queue is unreachable from the worker as well | the relay logs at `ERROR` and retries on the next loop; the row stays `pending` and `attempts` increments | nothing. **Nobody is alerted** — see `P-TKT-11` |

**Server-side validation.** `topic` must be one of the two members in the table above; any other value
is rejected at insert. `payload` must carry **exactly** the key set that table gives for that topic —
all of them and no others — so a `receipt.send` payload missing `message_version`, or carrying a fifth
key, is rejected at insert rather than left for a consumer to guess (`FR-ADR-059`). `dispatch_seq`:
integer, `>= 1`. `user_id` and `reset_token_id` are shaped by the account lane; what this specification
fixes about them is that they are the whole payload of `password_reset.send` and that **no token value
is among them**.

**Worked example — the window this closes.** A booking commits at `10:00:00.000Z`. The container is
killed at `10:00:00.004Z`, before the queue send. Under a post-commit send the job is gone and nothing
knows it was owed. Under this specification the `pending` row is in PostgreSQL; the worker's next loop
finds it — with a relay threshold of `OUTBOX_RELAY_MIN_AGE_SECONDS = 30` (**`ASSUMED`**, a starting
value, not a ruled one) and a long-poll wait of 20 seconds (`FR-ADR-059`), the receipt is enqueued
within roughly 30 to 50 seconds of the crash. *(reasoned from the configured values, not observed.)*

### `P-TKT-05` · Send exactly one receipt per booking, and retry the ones that fail · `RULED`
`[SRC: SRC-002 §8.5.1 · SRC-002 §8.5.2 · SRC-002 §E E-5 · SRC-003 OPEN-QUEUE-01 · SRC-003 OPEN-EMAIL-01 · FR-ADR-032 · FR-ADR-060 · FR-ADR-056 · FR-ADR-012]`
`[BRD: R-TKT-02]`

**Behaviour.** The worker claims the send with a durable row before it calls SES. The claim, not the
queue's configuration, is what makes a duplicate receipt impossible. A failed send is retried through
queue redelivery and eventually lands in the dead letter queue.

**The worker branches on `topic` before it does anything else.** One queue carries both members of
`P-TKT-04`'s vocabulary, so the first thing the receive loop does with a message is read its `topic`
and dispatch on it:

| `topic` | What runs |
|---|---|
| `receipt.send` | everything in this specification — the `receipt_dispatch` claim, the booking read, `SCR-TKT-02`, the SES call |
| `password_reset.send` | reads the `password_reset_token` row named by `reset_token_id`, renders the reset email and sends it through the same SES port. It takes **no** `receipt_dispatch` claim — that table is keyed on `booking_id` and this job has no booking. **Suppression, retry and failure are specified in `P-TKT-12`**, because a queue that is explicitly at-least-once cannot be left with one of its two message types unsuppressed |
| anything else | **the message is sent to the dead letter queue. It is not deleted** |

**An unrecognised `topic` is never deleted.** Deleting it destroys the only evidence that something
inserted a message this worker cannot handle — a version skew between a running worker and a newer API,
or a defect in whatever wrote the row. The message takes the ordinary failure route instead: it is
logged at `ERROR` with its `topic` and `request_id`, and **not** deleted, so redelivery exhausts
`maxReceiveCount` and the queue moves it to the dead letter queue. Nobody is watching that queue
(`P-TKT-11`), which is exactly why the message has to still be sitting in it when somebody finally
looks.

**Who may do it.** Nobody. The worker process only. **The API never calls SES** (`FR-ADR-060`).

**Preconditions.**
- `receipt_dispatch` exists, **unique on `booking_id`** (`FR-ADR-032`), with `status`
  (`pending` / `sending` / `sent` / `failed` / `suppressed`), `dispatch_seq` (integer, `>= 1`),
  `claimed_at`, `sent_at`, `ses_message_id`, `attempts`, `last_error`.
- **The row for this booking is already there.** It is created in the booking transaction with
  `dispatch_seq = 1`, `status = 'pending'`, `attempts = 0` (`P-TKT-04` happy path step 1). **The worker
  transitions it; the worker never inserts it.** `pending` is the state the row is created in and the
  state a resend returns it to (`P-TKT-07`). A row the **seed** created is `suppressed` and the worker
  never claims it (`P-TKT-04`).
- `MAIL_PROVIDER` is set with no default; `SES_SENDER_ADDRESS` is set with no default
  (`FR-ADR-060`, `FR-ADR-053`).

**Happy path** — the `receipt.send` branch.
1. The worker receives a message whose `topic` is `receipt.send`, carrying `booking_id`,
   `dispatch_seq`, `request_id`, `message_version`, and binds `request_id` to its logging context for
   the whole job (`FR-ADR-056`).
2. It claims the send by **updating the row that already exists**. There is no insert and no
   `ON CONFLICT`, because `P-TKT-04` wrote the row inside the booking transaction:
   `UPDATE receipt_dispatch SET status='sending', claimed_at=now(), attempts=attempts+1
   WHERE booking_id = :booking_id
     AND dispatch_seq = :dispatch_seq
     AND (status = 'pending'
          OR status = 'failed'
          OR (status = 'sending' AND claimed_at < now() - :stale_interval))
   RETURNING id`, where `:stale_interval` is `RECEIPT_CLAIM_STALE_SECONDS`.
   **Zero rows returned means another delivery owns this send, or it is already sent, or this message
   is a stale copy from an earlier `dispatch_seq`.** The worker deletes the queue message and stops.
   There is still exactly one row per booking, which is what `FR-ADR-032` requires.
3. It reads the current booking from PostgreSQL — the payload carries no booking data.
4. It renders the receipt (`SCR-TKT-02`) and calls SES through the mail port **under
   `SES_SEND_TIMEOUT_MS`**. See the block below: without a bound, a hung call holds the claim in
   `sending` and no redelivery can take it for `RECEIPT_CLAIM_STALE_SECONDS`.
5. On success it sets `status='sent'`, `sent_at=now()`, `ses_message_id=<the id SES returned>`, and
   deletes the queue message. **`sent` means SES accepted the message for delivery. It does not mean
   the customer received it, and no later event ever revises it** — `P-TKT-11` states what that table
   can and cannot answer.

**The SES call is bounded, and the bound is what keeps a dead worker from costing fifteen minutes.**

`SES_SEND_TIMEOUT_MS = 5000` (**`ASSUMED`** — no source states a figure). **The ordering around it is
not assumed**, and it is bounded on both sides:

- **It must be far shorter than the queue's visibility timeout** — 120 seconds in the worked example
  below — so this delivery reaches a terminal state, `sent` or `failed`, before the next redelivery
  arrives. A send still running when its own redelivery lands is how two deliveries end up in the same
  job, and only the claim then stands between the customer and two receipts.
- **It must be shorter than the worker's drain.** On SIGTERM the worker "finishes the message it is
  handling" (`P-XCT-17` exception 5), so an unbounded SES call makes an unbounded drain, and SIGKILL
  arrives mid-send. At 5000 ms it is a quarter of `SHUTDOWN_DRAIN_TIMEOUT_SECONDS` (20 s, `S7.9`).
- **It must be comfortably longer than a normal in-region `SendEmail` round trip**, or ordinary
  receipts fail under no fault at all. *(reasoned from the configured values, not observed — nothing
  in this project has called SES.)*

**What the absence of it cost, stated because it is the reason this paragraph exists.** With no
timeout the call can hang indefinitely. The row stays `sending` with a live `claimed_at`, so every
redelivery reads the claim as held and deletes its own message (the claim table below), and **no
delivery can retake the send until `RECEIPT_CLAIM_STALE_SECONDS` — 900 seconds — has elapsed.** For
fifteen minutes the customer has paid, no receipt has gone out, nothing is being attempted, and
`P-TKT-11` means nobody is told. With the bound the same failure lands on `failed` in five seconds and
the next redelivery claims it (exception row 3).

**A timeout is not a known failure, and this is the one place `FR-ADR-032`'s guarantee does not
reach.** On a timeout the worker does not know what SES did: the message may have been accepted and
the response lost. The claim makes **two senders** impossible; it cannot make **two sends** impossible
when the first sender never learned its own outcome. So a retry after a timeout can deliver a second
identical receipt. **That is the lesser of the two outcomes and it is chosen deliberately**: the
alternative — never retrying a send whose outcome is unknown — is a customer who has paid, cannot
enter, and has nothing coming. `SCR-TKT-02`'s re-sent state already renders a second copy
byte-identically for exactly this reason. `last_error` records that the call **timed out** rather than
that SES **refused**, so the two are distinguishable afterwards by the operator `P-TKT-11` describes.

**What the claim does with every status it can find.** Stated exhaustively, because the row now exists
before the worker ever sees it and a reader has to be able to tell a first delivery from a reclaim
without inferring it from the `UPDATE`'s `WHERE` clause.

| Status found | `dispatch_seq` matches | What the claim does |
|---|---|---|
| `pending` | yes | **Claims it.** `status='sending'`, `claimed_at=now()`, `attempts` goes `0 → 1`. This is the ordinary first delivery, and it is the only transition out of the state `P-TKT-04` created |
| `sending`, `claimed_at` newer than `RECEIPT_CLAIM_STALE_SECONDS` | yes | Nothing. Another delivery is running. Zero rows, the message is deleted, one `INFO` line |
| `sending`, `claimed_at` older than `RECEIPT_CLAIM_STALE_SECONDS` | yes | **Reclaims it.** The previous worker died mid-send. `claimed_at=now()`, `attempts` increments |
| `sent` | yes | Nothing. The receipt went out. Zero rows, the message is deleted. **A `sent` claim is never reclaimed by a redelivery** (`FR-ADR-032`); only `P-TKT-07` moves it, and it does so by raising `dispatch_seq` |
| `failed` | yes | **Claims it.** A failed send is retryable — that is what the redelivery is for |
| `suppressed` | yes | Nothing. `suppressed` is absent from the claim's `WHERE` clause, so the `UPDATE` matches no row without any extra branch being written. Zero rows, the message is deleted, one `WARNING` line naming the `booking_id`. **The message should not have existed**: the seed enqueues no receipt job (`P-TKT-04`), so a `receipt.send` message naming a suppressed row means something outside the seed wrote one. It is logged at `WARNING` rather than `INFO` for that reason, and it is still never sent — the address cannot receive mail (`FR-ADR-060`) |
| any of the five | no | Nothing. The message is a stale copy from before a resend raised the sequence. Zero rows, the message is deleted |
| no row at all | — | Zero rows, the message is deleted, logged at `ERROR`. **Unreachable once `P-TKT-04` is implemented**, because the row and the message are written in one transaction, and the seed writes a row for every booking it creates. It is stated so the code has a defined branch rather than an unhandled empty result |

**The state machine, proved complete.** Five states and three inputs, so fifteen pairs, and the claim
table above covers the worker's column of it. Written out because adding a state that only an
out-of-band writer produces is exactly the kind a reachability argument otherwise misses.

| Status | Reached by | A `receipt.send` delivery (`P-TKT-05`) | A resend request (`P-TKT-07`) | The SES call returning |
|---|---|---|---|---|
| `pending` | `P-TKT-04`, in the booking transaction | claims it → `sending` | refused, 202 `queued: false` (`attempts = 0`) or 202 `queued: false` (`attempts > 0`) | n/a — no claim is held |
| `sending` | the claim | live claim → nothing; stale claim → reclaims it | refused, 202 `queued: false` | success → `sent`; error **or timeout** → `failed` |
| `sent` | a successful SES call | nothing; the message is deleted | accepted → `dispatch_seq + 1`, back to `pending` | n/a |
| `failed` | an SES error | claims it → `sending` | accepted → `dispatch_seq + 1`, back to `pending` | n/a |
| `suppressed` | **the seed script only** (`P-XCT-30`, `P-XCT-32`) | nothing; the message is deleted and logged at `WARNING` | **refused, 409** (`P-TKT-07` exception 8) | n/a |

- **No unreachable state.** Every row's *Reached by* cell names a writer. `suppressed` is reachable
  because the seed writes it, which is the whole reason it is not simply a state the schema forbids.
- **No unhandled input.** Every cell is filled. The `n/a` cells are not gaps: SES cannot return against
  a row no claim is held on, because a claim is what precedes an SES call (`P-TKT-05` happy path steps
  2 and 4).
- **`suppressed` has no outgoing edge, deliberately.** Nothing in the application moves a row out of
  it. A resend is refused rather than accepted, so it cannot become `pending`; the worker never claims
  it, so it cannot become `sending`. It is terminal because the fact it records — that no send was ever
  attempted for a booking whose address cannot receive mail — does not stop being true.
- **`suppressed` has no incoming edge from any other state either.** It is written at insert, by the
  seed, and by nothing else. A row that started `pending` never becomes `suppressed`, which is what
  keeps the state meaning "this was never real" rather than "somebody gave up on this".

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | The claim returns zero rows (a duplicate delivery, or an older `dispatch_seq`) | the message is deleted, no email is sent, one `INFO` line is logged | nothing. This is the mechanism working |
| 2 | SES returns an error | `status='failed'`, `last_error` set, **the queue message is not deleted**, so it is redelivered | nothing on the site |
| 2a | **The SES call does not answer within `SES_SEND_TIMEOUT_MS`** | treated as row 2 — `status='failed'`, **`last_error` records that the call timed out rather than that SES refused**, the message is not deleted and is redelivered. **The outcome of the abandoned call is unknown**, so the retry may deliver a second identical receipt; see the block above | nothing on the site. A second copy of the same receipt, if the first one was in fact accepted |
| 3 | A redelivery arrives for a `failed` claim | the claim is retryable and the send is attempted again | nothing |
| 4 | The worker is killed mid-send, leaving `sending` | after `RECEIPT_CLAIM_STALE_SECONDS` the claim is reclaimable by a later delivery | nothing |
| 5 | Redelivery exceeds the queue's `maxReceiveCount` | the message moves to the dead letter queue. The `receipt_dispatch` row stays `failed` with the SES error | **nothing.** See `P-TKT-11` and `P-TKT-10` |
| 6 | SES is in sandbox and the address is not verified | SES refuses. Treated as row 2, then row 5 | nothing |
| 7 | A message arrives whose `topic` is neither `receipt.send` nor `password_reset.send` | logged at `ERROR` with the `topic` and `request_id`, **not deleted**; redelivery carries it to the dead letter queue | nothing |

**Server-side validation.** `message_version` must be a known version; an unknown version is logged at
`ERROR` and the message is left for the dead letter path rather than being parsed optimistically.
`topic` must be a member of `P-TKT-04`'s vocabulary; anything else takes the dead letter route above.

On the `receipt.send` branch only: `dispatch_seq` must be a positive integer, and `booking_id` must
resolve to a confirmed booking — **a `receipt.send` message whose booking does not resolve is logged
and deleted**, because redelivering it forever achieves nothing. **That deletion rule belongs to
`receipt.send` alone and may not be generalised to the queue.** A `password_reset.send` message carries
no `booking_id` at all, and applying the booking check to it would delete the one message a locked-out
customer's account recovery depends on. A message on an unrecognised topic is sent to the dead letter
queue rather than deleted, because deleting a message nobody recognises destroys the evidence of the
defect that produced it.

**Logging rule, stated because it is easy to breach:** the worker's log lines carry `booking_id` and
`request_id`. **A log line may never carry the booking reference and the customer's email address
together** (`FR-ADR-056`) — the pair is enough to walk into a hall.

**SES starts sandboxed, so this path fires on every test.** In sandbox SES sends only to verified
addresses (`FR-ADR-060`), so every test booking made to an unverified address exercises rows 2, 3 and 5
above and ends in the dead letter queue. That is useful, because the failure path gets exercised. **It
is not the ruled behaviour of a live system and must never be read as one** (`FR-ADR-049`).

**Worked example — the stale claim.** The queue's visibility timeout is a Zone C value the client sets;
the specification in `docs/30 Deployment/` states the application expects it to exceed the worst-case
SES call plus processing time (`FR-ADR-059`). Take a visibility timeout of **120** seconds and
`RECEIPT_CLAIM_STALE_SECONDS = 900`.

The worker claims at `10:00:00Z` and is killed at `10:00:01Z`, leaving the row `sending` with
`claimed_at = 10:00:00Z`. The queue redelivers every 120 seconds, and each redelivery compares the
claim's age against 900:

| Redelivery | Claim age | `age > 900`? | Outcome |
|---|---|---|---|
| `10:02:00Z` | 120 s | no | live `sending` claim; zero rows; the message is deleted |
| `10:04:00Z` | 240 s | no | as above |
| `10:06:00Z` | 360 s | no | as above |
| `10:08:00Z` | 480 s | no | as above |
| `10:10:00Z` | 600 s | no | as above |
| `10:12:00Z` | 720 s | no | as above |
| `10:14:00Z` | 840 s | no | as above |
| `10:16:00Z` | **960 s** | **yes** | the claim is reclaimed, `attempts` increments, and the send proceeds |

So the receipt goes out at about `10:16:00Z` — **a delayed receipt, never a duplicate one.**

**The safety property, restated against 900.** `RECEIPT_CLAIM_STALE_SECONDS` must exceed the queue's
visibility timeout, or a redelivery arriving while the first attempt is still running would find the
claim stale, take it, and send a second email. `900 > 120` holds with a wide margin — 900 is seven and
a half visibility timeouts — so the property is satisfied more strongly at 900 than it was at 300.
**That ordering is the whole point of the number**, and it is a rule about two values rather than a
value in itself: if the client raises the visibility timeout past 900, this variable has to move too
(`FR-ADR-059`).

**What the larger threshold costs, stated rather than glossed.** Eight redeliveries are spent before
the reclaim instead of three, and each one consumes a receive against `maxReceiveCount`. If the
client's `maxReceiveCount` is not greater than eight, the message reaches the dead letter queue before
the claim ever goes stale, and the receipt is not sent at all until a person looks. **No value is set
here** — `maxReceiveCount` is a Zone C value (`SRC-002 §6.3.6`) — but the arithmetic above is what the
deployment specification has to put in front of the client, because a default chosen without it
produces a silently unsent receipt. *(reasoned from the configured values, not observed.)*

**The two rules this lane owes `docs/30 Deployment/`, written out here in the form they have to reach
the client — because as of this pass they are not there.** `docs/30 Deployment/` holds one file,
`AWS_PREP_QUEUE.md`, and its SQS entry (row 9, `REQUESTED`) names the queue and its dead letter queue
and **neither of these two values**. Both are Zone C settings the application cannot read
(`FR-ADR-032`), so no boot check and no test can catch either one, and both fail silently in opposite
directions:

| # | The rule | What a wrong value does, with nothing reporting it |
|---|---|---|
| 1 | **The queue's visibility timeout must be less than `RECEIPT_CLAIM_STALE_SECONDS`** (900) | A visibility timeout above 900 means a redelivery arrives while the first attempt is still running, finds the claim stale, takes it, and **sends a second receipt**. The property this whole specification is built on stops holding, and nothing errors |
| 2 | **`maxReceiveCount` must be greater than `ceil(RECEIPT_CLAIM_STALE_SECONDS / visibility_timeout)`** — `ceil(900 / 120) = 8` at the worked pair, so **greater than 8** | At 8 or fewer the message is in the dead letter queue **before** the claim ever goes stale, so the reclaim in the table above never happens and **the receipt is never sent**. Dead letter queue depth is not alarmed (`P-TKT-11`), so nothing reports it |

The second rule is stated as arithmetic rather than as the number 8 on purpose: **8 is derived from
the pair, not chosen**, so a client who changes the visibility timeout changes the required
`maxReceiveCount` with it. At 120 seconds the eighth redelivery is the first whose claim age (960 s)
exceeds 900, and it is the ninth receive of the message counting the original delivery — which is why
`maxReceiveCount` must exceed 8 rather than reach it. **Both rules belong in the SQS row of the prep
queue and neither is there yet; this lane owes it and the debt is recorded here rather than assumed
paid.** *(reasoned from the configured values, not observed.)*

### `P-TKT-06` · What the receipt carries · `RULED`
`[SRC: SRC-001 §5.3.4 · SRC-001 §E E-9 · SRC-002 §E E-5 · SRC-003 OPEN-TICKET-01 · SRC-003 OPEN-LOCALE-01 · FR-ADR-048 · FR-ADR-018 · FR-ADR-036 · FR-ADR-060]`
`[BRD: R-TKT-02 · R-TKT-01]`

**Behaviour.** The receipt email carries the booking reference, the seat numbers, the hall, the
showtime, the film title and the amount paid, addressed to the account's own email address. **No QR
code, no barcode, no attachment, and no image.**

**Who may do it.** The worker process only, on behalf of the booking's owner. The delivery address is
the account's email address (`FR-ADR-014`); it is never taken from a request.

**Preconditions.**
- A claim has been taken (`P-TKT-05`).
- The booking, its seats, its showtime, its screen and its movie all resolve.

**Happy path.**
1. Read the booking and its related rows from PostgreSQL.
2. Render the showtime in **Asia/Kolkata** from the stored UTC instant (`FR-ADR-018`).
3. Render the seat labels **ordered by row letter, then by seat number compared as an integer**
   (`E5 P-ACC-10`) — `F7, F8, F9`, never the insertion order `F9, F7, F8`, which is what a seat added
   to a hall already in service produces (`E6 P-ADM-14`). The receipt and the door are the two places
   the order is read aloud.
4. Render the total from the stored integer paise at the last possible moment, with Indian digit
   grouping and the `₹` symbol (`FR-ADR-036`). **No tax line, no fee line, no discount line, and no
   space left for one** (`FR-ADR-040`).
5. Render the reference in the `FR-XXXX-XXXX` presentation form.
6. Send both a plain-text part and a minimal HTML part with the same content. `SCR-TKT-02` holds the
   exact copy.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | The movie, screen or showtime row cannot be read | the send is abandoned, `status='failed'`, `last_error` records which join failed, the message is redelivered | nothing. A receipt with a missing hall is worse than a late one |
| 2 | The account has no email address | impossible by construction — an account cannot exist without one (`FR-ADR-050`). If it occurs it is `failed` with that error | nothing |

**Server-side validation.** Every field rendered into the receipt is read from the database in the
same read; none is passed in. The reference is re-formatted from the stored 8 characters rather than
carried through the queue, so a receipt can never show a reference that the database does not hold.

**What is never in it:** no card number, CVV, expiry or any placeholder for one — payment is simulated
and the system holds no card data at all (`SRC-003 OPEN-PAY-01`); no QR code (`SRC-002 §E E-5`); no
poster or any other image, because `OPEN-ATTRIB-01` is open and no licensed material may enter this
product; no PDF attachment (`FR-ADR-048` rejected it); no password, token or link that signs anybody
in.

**Worked example.** Booking `FR-ABCD-EFGH`, three Premium seats `F7`, `F8`, `F9` in `Hall 3`, showtime
stored as `2026-08-21T13:45:00Z`, total `84372` paise — the seeded figures worked through in
`P-TKT-03`. The receipt renders the time as
**21 Aug 2026, 7:15 pm (Asia/Kolkata)** and the amount as **₹843.72**. That is `S7.19`'s
date-with-time form plus the zone suffix its rule 2 gives the emailed receipt and nothing else, on the
grounds that a receipt is the one surface read outside the site and months later. The exact rendered
strings are in `SCR-TKT-02`.

### `P-TKT-07` · Re-send a receipt on request · `RULED`
`[SRC: SRC-003 OPEN-EMAIL-01 · FR-ADR-048 · FR-ADR-032 · FR-ADR-031 · FR-ADR-058 · FR-ADR-019 · FR-ADR-060 · FR-ADR-067]`
`[BRD: R-TKT-03 · R-TKT-02]`

**Behaviour.** The owner of a booking, or an admin, can ask for the receipt to be sent again. The
request increments the dispatch sequence on the claim row and inserts a new outbox row in one
transaction. It is rate limited per booking. **It is a convenience for a customer who deleted the
email. It is not the answer to SES failing** (`FR-ADR-048`), because a customer who never received
anything may not know to look.

**Who may do it.** The booking's owner, and nobody else. **No role is exempt and there is no override**
— the same rule as `P-TKT-09` and `EP-TKT-01`, and agreeing with `P-ACC-12`. Enforced once on the
router as a dependency: authenticated, then the ownership rule. Never per handler.

**Why an admin override was removed rather than kept.** This endpoint's `202` body carries the
customer's email address, so an override would make it a customer-record read by another route — and
`P-TKT-02` resolves the reference identically for a non-owner and a stranger, which would have made
the override unreachable in any case. An admin who must answer for a receipt reads the change log and
`receipt_dispatch`, which record what happened without disclosing the address.

**Preconditions.**
- The booking exists and resolves for this caller.
- A `receipt_dispatch` row exists for it. **This is always true for a confirmed booking**, because the
  row is created in the booking transaction (`P-TKT-04` step 1) and nothing deletes it. It is true in
  particular while the worker is down — which is the state a resend is most likely to arrive in, and
  the state under which "a row exists" was previously an assumption with no behaviour behind it.
  **It is also true for a seeded booking**, whose row the seed writes `suppressed` (`P-TKT-04`,
  `P-XCT-30`). All **11,003** demonstration bookings were the case that made "always true" false — the
  figure is `P-XCT-30`'s, derived from its own occupancy rule; this row previously said "roughly sixty",
  which was computed from nothing. They
  now have a row, and step 2 below says what happens when this control finds one.
- The per-booking rate-limit bucket has a token. **This is a precondition of the accepting branch
  only** (step 5). Steps 2, 3 and 4 refuse without spending one and without needing one, which is why
  a customer who presses the control while the worker is down is not locked out of the resend they
  will legitimately want minutes later, and why a seeded booking returns the same 409 on every press
  rather than a 429 on the second.

**Happy path.**
1. `SELECT ... FOR UPDATE` the `receipt_dispatch` row for this booking. It exists.
2. **If `status = 'suppressed'`, this is a seeded booking.** Enqueue nothing, change nothing, spend no
   token, and return `409 RECEIPT_SUPPRESSED`. This is checked **first**, before every other branch,
   because it is the one state in which no amount of waiting or retrying changes the outcome. See
   exception row 8.
3. **If `status = 'pending'` and `attempts = 0`, the first receipt has not been attempted yet.**
   Enqueue nothing, change nothing, spend no token, and return 202 with `queued: false`. There is
   already an unclaimed `outbox_message` for this booking; a second one buys nothing and the customer
   has not yet failed to receive anything. See exception row 3.
4. **If `status = 'sending'`, or `status = 'pending'` with `attempts > 0`** — a resend is already
   enqueued and not yet claimed — **enqueue nothing** and return 202 with `queued: false`. A dispatch
   is already in flight; adding a second is how a customer gets two receipts. (`attempts` is what
   separates this case from step 3: it is `0` only on a row no worker has ever claimed.)
5. Otherwise — `sent` or `failed` — set `dispatch_seq = dispatch_seq + 1`, `status = 'pending'`, and
   insert an `outbox_message` with `topic = 'receipt.send'` carrying the new `dispatch_seq`, in the
   same transaction.
6. Commit, then run the fast-path relay exactly as `P-TKT-04` step 3.
7. **No `audit_log` row is written, on any branch of this specification.** A resend is the booking's
   own owner asking for their own receipt again, and no other caller can reach it — no role is exempt
   and there is no override (see *Who may do it* above). That makes it a customer action on the
   customer's own record, not a privileged write, and `P-ADM-19` owns a **closed** audit action
   vocabulary that contains nothing for it. Writing one would require inventing an action name and
   would record the booking's owner as if they were an operator.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | Not signed in | 401 `AUTH_REQUIRED` | "Sign in to see this booking." |
| 2 | The reference does not resolve for this caller | 404 `NOT_FOUND` | "No booking with that reference is on your account." |
| 3 | **The first receipt has not been attempted yet** — the `receipt_dispatch` row is `pending` with `attempts = 0`, which is the state a resend hits while the worker is down | 202, `queued: false`, nothing enqueued, nothing changed, no token spent | "The first receipt has not been sent yet. Wait for it to arrive before requesting another." |
| 4 | A dispatch is already in flight — `sending`, or `pending` with `attempts > 0` | 202, `queued: false`, nothing enqueued | "A receipt is already being sent for this booking." |
| 5 | **The per-booking interval has not elapsed** — `RECEIPT_RESEND_MIN_INTERVAL_SECONDS = 300`, so `Retry-After = 300 − elapsed`; at 60 seconds elapsed that is 240 | 429 `RATE_LIMITED` with `Retry-After: 240` | "A receipt was requested recently. You can request another in 4 minutes." |
| 5a | **The per-user lookup bucket is empty** — `RATE_LIMIT_LOOKUP_USER_PER_MIN`, 20 per minute, which this endpoint shares with `EP-TKT-01` (`FR-ADR-058`) | 429 `RATE_LIMITED` with `Retry-After: 3` | "Too many attempts. Try again in 3 seconds." |
| 5b | **The per-IP lookup bucket is empty** — `RATE_LIMIT_LOOKUP_IP_PER_MIN`, 60 per minute, which this endpoint also shares with `EP-TKT-01` (`S7.4`) and which **refuses first when several callers share one address** | 429 `RATE_LIMITED` with `Retry-After: 1` | "Too many attempts. Try again in 1 second." |
| 6 | Redis is unreachable, so the limiter fails closed | 503 `DEPENDENCY_UNAVAILABLE` | "This is unavailable right now. Your booking is not affected." |
| 7 | The insert fails | 500 `INTERNAL_ERROR`, nothing enqueued | "Something went wrong and no receipt was requested. If you need help, quote `a1b2c3d4`." |
| 8 | **The `receipt_dispatch` row is `suppressed`** — this is a seeded demonstration booking (`P-TKT-04`) | 409 `RECEIPT_SUPPRESSED`, nothing enqueued, nothing changed, **no token spent** | "This is demonstration data. No receipt was sent for this booking and none can be — the address is a placeholder, not a real inbox." |

**Rows 5, 5a and 5b are three rows for the same reason rows 6 and 7 of `P-TKT-02` are.** **Three**
limiters guard this endpoint — `S7.4` gives the resend a per-booking interval, a per-user bucket and a
per-IP bucket — they produce figures three orders of magnitude apart, and the header carries whichever
one refused (`S7.20`). Publishing only "4 minutes" against a trigger that read "the per-booking **or**
per-user bucket" told an engineer to render 240 seconds for a bucket that yields 3.

**Row 5b was still missing after that split and is added here.** It is the same incompleteness
`P-ACC-12` added its own row 5 to fix, on the same pair of buckets: a table that derives only the
narrower limiter is incomplete, because **the wider one refuses first for a caller behind a shared
address** — a cinema's public wifi, an office, a mobile carrier's NAT. Its figure is
`ceil(60 / 60) = 1`, and **the singular is copy that ships**: `S7.20` names this bucket as one of only
four in the product that reach `Retry-After: 1`, so an implementer writing `"{n} seconds"`
unconditionally puts "1 seconds" on a live path. **The per-booking
figure is the one that moves**: it is an interval rather than a refill, so it counts down from 300 and
the "4 minutes" in the copy is the worked value at 60 seconds elapsed, never a constant
(`FR-ADR-058`).

**Why row 8 is a refusal and not a policy.** Every seeded account sits on the reserved
`SEED_EMAIL_DOMAIN`, which cannot resolve (`FR-ADR-067`); SES starts sandboxed and refuses every send
to an unverified address, and out of the sandbox those sends are hard bounces against the sending
identity's reputation (`FR-ADR-060`). **So the 409 is not a choice about what a resend ought to do —
it is the only outcome the environment can produce**, said in advance instead of after a message has
been queued, retried `maxReceiveCount` times and dead-lettered where nobody watches (`P-TKT-11`).
`409` rather than `422` because nothing about the request is malformed: it is a well-formed request
against a row whose state forbids it, which is what every other 409 in this product means.
**No token is spent**, for the same reason as row 3 — refusing to do work is not work, and there is no
rate a caller could pick that would make this booking sendable.

Row 3 is the row that was missing. Under the older reading — the `receipt_dispatch` row created by the
worker's claim — a resend arriving before the worker had ever run found no row at all, and this table
said nothing about what happened next. The row is now created with the booking, so the state is
reachable, named, and refused rather than left to whoever writes the handler.

**Server-side validation.** No request body. The `reference` path parameter is validated by
`P-TKT-02`. The per-booking interval is
`RECEIPT_RESEND_MIN_INTERVAL_SECONDS = 300` (**`ASSUMED`** — `FR-ADR-048` rules that the control is
rate limited per booking and does not state a value; `FR-ADR-058`'s table has no row for it). The
per-user bucket reuses `FR-ADR-058`'s booking-lookup bucket of 20 per minute.

**Worked example — the resend a `pending` row refuses, and the `Retry-After` figure on the one it
accepts.** Booking `FR-ABCD-EFGH` commits at `17:55:00` local. The `receipt_dispatch` row is written in
the same transaction: `dispatch_seq = 1`, `status = 'pending'`, `attempts = 0`. The worker is down.

| When | Row state read under `FOR UPDATE` | Outcome |
|---|---|---|
| `17:56:00` | `pending`, `attempts = 0` | **Refused as unnecessary** (row 3). 202, `queued: false`, nothing enqueued, no token spent. The customer is told the first receipt has not been sent yet |
| `18:00:00` | the worker returns and claims: `pending → sending`, `attempts` `0 → 1`; the send succeeds; `status = 'sent'` | the receipt arrives |
| `18:00:10` | `sent` | **Accepted.** `dispatch_seq` `1 → 2`, `status` back to `pending`, one `outbox_message` inserted with `dispatch_seq = 2`, and the per-booking bucket spends its token |
| `18:01:10` | — | **429.** Sixty seconds after an accepted resend, with `RECEIPT_RESEND_MIN_INTERVAL_SECONDS = 300`, the header is `Retry-After: 300 - 60 = 240` and the message renders 240 seconds as "4 minutes" |

The `Retry-After` value is computed from the bucket's refill, never from a constant in the copy
(`FR-ADR-058`). Note what the `17:56:00` request did **not** do: it spent no token, so the customer who
tries once while the worker is down is not locked out of the resend they will legitimately want at
`18:00:10`.

If a copy of the `dispatch_seq = 1` message is still on the queue after `18:00:10`, it no longer
matches the row's sequence, so `P-TKT-05`'s claim returns zero rows for it and it is deleted. **One
row, one sequence, one receipt per accepted press.**

**Worked example — the same control against a seeded booking.** `customer-07@demo.frontrow.invalid`
signs in with the seeded password (`P-XCT-32`) and opens one of the seeded bookings. Its
`receipt_dispatch` row reads `dispatch_seq = 1`, `status = 'suppressed'`, `attempts = 0`. The resend
control returns `409 RECEIPT_SUPPRESSED` on the first press and on the hundredth: nothing is enqueued,
`dispatch_seq` stays at `1`, the row's status does not move, and the per-booking bucket still holds a
full token. The outcome is identical every time, which is what makes it a state and not a race.

### `P-TKT-08` · Entry at the door is a manual human check · `RULED`
`[SRC: SRC-003 OPEN-TICKET-01 · SRC-003 OPEN-TICKET-02 · SRC-001 §E E-3 · SRC-001 §E E-9 · SRC-002 §E E-5 · FR-ADR-048 · FR-ADR-015]`
`[BRD: R-TKT-05]`

**Behaviour.** A person at the entrance reads the reference from the customer's receipt or from the
booking page on their phone and checks it by hand. **The product provides nothing for this.** There is
no scanner, no validation endpoint, no door screen, no staff account, and no state anywhere that
records a reference as having been used.

**Who may do it.** Nobody in the system. There is no cinema-staff role (`SRC-001 §E E-1`). The person
at the door has no account and no interface, and the check is a business process, not a feature.

**Preconditions.** None in software.

**Happy path.**
1. The customer presents the reference — from the emailed receipt, from `SCR-TKT-01`, or read aloud.
2. A person compares it against the day's bookings by whatever means the venue uses.
3. Nothing is written. No endpoint is called. No row changes.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | The same reference is presented twice, by two different people | **nothing happens.** No software detects it | nothing — there is no screen |
| 2 | A reference is invented at the door | nothing in the product checks it | nothing |
| 3 | A door attendant asks for an app to scan with | there is none, by ruling | nothing |

**Server-side validation.** None — there is no request. `EP-TKT-01` exists so a **customer** can find
their own booking again; it is authenticated and returns only the caller's own booking, and it is
**not** an entry-validation endpoint. Reading it as one would build the thing `OPEN-TICKET-02`
refused.

**Accepted weakness, stated plainly.** **Nothing prevents the same reference being presented twice.**
Two people holding the same eight characters both get in, and the system cannot tell. That is accepted
for a demonstration project and it is a real hole in a live one (`SRC-003 OPEN-TICKET-02`,
`FR-ADR-015`, `FR-ADR-048`). It is recorded in the architecture folder's list of deliberate gaps and
it is not solved here.

### `P-TKT-09` · Look up a booking by its reference · `RULED`
`[SRC: SRC-001 §5.4.2 · SRC-003 OPEN-BOOK-02 · FR-ADR-015 · FR-ADR-048 · FR-ADR-058 · FR-ADR-013]`
`[BRD: R-TKT-03 · R-TKT-04]`

**Behaviour.** An authenticated caller can read one booking by its reference, **and only a booking that
is their own.** The response carries the facts a customer needs at a door.

**There is no admin override on this endpoint, for any role.** No frozen source and no approved record
grants an admin the right to read an individual customer's booking. `FR-ADR-009` makes `admin` a
superset of *manager*, and a manager is read-only **reporting**; `SRC-001 §7.6`'s "who booked this seat
and when" is answered by the change log and the Phase 8 dashboard, not by a customer-facing booking
endpoint. Granting the override would be inventing a privilege nobody wrote, and **adopting the
stricter reading is not a waiver and needs no signature** (`CONSTITUTION.md` Art III.10). The account
lane states the same rule from the other side — `P-ACC-12`: "there is no v1 endpoint by which an admin
reads another customer's bookings" — and **this is the endpoint it is talking about.** An admin who has
to answer for a booking uses the change log and the dashboard; **this is deliberately not a
customer-record lookup**, and it is the one value that admits a person to a hall.

**Who may do it.** Any authenticated account. **The role is not consulted at all.** The rule is
**ownership, and only ownership**: the caller may read a booking whose `user_id` equals their own, and
that is the whole rule for `customer`, `manager` and `admin` alike. Applied once as a router
dependency, never inside the handler (`SRC-001 §7.4`). Another account's booking returns the same 404
as a reference that does not exist (`P-TKT-02` rows 2, 3 and 4 are byte-identical), so the endpoint
tells an admin exactly what it tells a stranger.

**Preconditions.**
- The caller is authenticated.
- The rate-limit buckets have tokens (`FR-ADR-058`: 20 per minute per user, 60 per minute per IP).

**Happy path.**
1. Normalise the reference (`P-TKT-02`).
2. Load the booking with its seats, screen, showtime and movie in one read.
3. Apply the ownership rule.
4. Return the reference in presentation form, the film title, the hall name, **the showtime as one
   instant carrying the cinema's UTC offset**, the seat labels **in the order `E5 P-ACC-10` fixes**,
   the total in integer paise, the instant payment was captured, and the account email address the
   receipt is addressed to.

**One instant, with the offset on it, and no second local field.** This endpoint previously returned
`starts_at` in bare UTC **and** a separate `starts_at_local` described only as "ISO-8601 local time in
Asia/Kolkata". Both halves were defects. The zone was **hardcoded into a wire contract** while
`E6 P-ADM-26` makes the venue's zone an editable property of the `cinema` row that `EP-ADM-29` can
change — after which the field's own description would be false and nothing would fail. And the
description never said whether the local value carried an offset, so an API client could not tell
whether `2026-08-21T19:15:00` or `2026-08-21T19:15:00+05:30` was correct, which is a coin toss on the
one value that tells a customer when to arrive.

`2026-08-21T19:15:00+05:30` **is** the local time and the instant at once, which is why one field
replaces two: it needs no zone name to be interpretable, it is unambiguous to a client, and it is the
shape every other customer-facing endpoint in the product now uses (`E5 P-ACC-10`, `P-BRW-06`). The
offset is serialised from the `cinema` row, and **the client never converts** — a client converting UTC
is a second implementation of `FR-ADR-018`, and it is the one that is wrong on a device whose clock is
set to another country. `paid_at` takes the same treatment because it is rendered on the same page.
**This is a wire change and the merge owner regenerates the contract.**

**Exception paths.** As `P-TKT-02`'s table, in full. Rows 2, 3 and 4 of that table are byte-identical
by design.

**Server-side validation.** `reference`: string, 1..64, normalised then matched exactly. No query
parameters, no body. The response contains **no booking status and no `cancelled_at`** — both columns
exist in the schema and **no v1 endpoint exposes them** (`FR-ADR-013`).

**What this endpoint deliberately does not return: the receipt's dispatch state.** The
`receipt_dispatch` row records whether the send is `pending`, `sending`, `sent`, `failed` or
`suppressed` (`P-TKT-04`, `P-TKT-05`), and **that
state is not on the customer API in v1.** Putting it there would require the interface to render
something for `failed`, and what a customer is told in that case is `OPEN-EMAILFAIL-01`, reserved
(`FR-ADR-049`). An operator-facing view of the same data belongs to the Phase 8 dashboard and is not
specified in this lane.

### `P-TKT-10` · What the customer is told when the receipt definitively fails · **`OPEN`**
`[SRC: SRC-003 OPEN-EMAILFAIL-01 · SRC-003 OPEN-EMAIL-01 · SRC-003 OPEN-TICKET-01 · FR-ADR-049 · FR-ADR-013]`
`[BRD: R-TKT-06]`

**Status is `OPEN` and this specification decides nothing.** `OPEN-EMAILFAIL-01` is a live Article X
row, owned by the client, class reserved: product. **No sentence shown to a customer whose receipt
definitively failed appears anywhere in this document, and none may be added by anyone reading it.**
A plausible sentence written into that screen would close a question nobody answered, which is the
cardinal failure this project exists to prevent (`CONSTITUTION.md` Art VII.3, mirrored in
`SRC-003 OPEN-EMAILFAIL-01`).

**What is specified here — the surface, and only the surface.**

**Behaviour.** The system records the state of every receipt send and gives the customer routes to the
reference that never depended on the email. It changes no booking state on a failed send and it emits
no customer-facing message about one.

**Who may do it.** Not applicable. There is no action.

**What state exists** — all of it already built by the specifications above:

| Where | What it holds |
|---|---|
| `receipt_dispatch` (one row per booking, created with the booking in `P-TKT-04`, transitioned by `P-TKT-05`) | `status` of `pending` / `sending` / `sent` / `failed` / `suppressed`, `attempts`, `last_error` carrying the SES error, `ses_message_id` on success, `dispatch_seq`. **`suppressed` is not a failure and is not part of this question** — it belongs only to seeded demonstration bookings, for which no send was ever attempted and no real customer paid (`P-TKT-04`) |
| `outbox_message` (`P-TKT-04`) | that the job was created and whether it reached the queue |
| the dead letter queue (`FR-ADR-059`) | the messages whose send failed past `maxReceiveCount` |
| `booking` | **unchanged.** A failed send alters no booking field. The booking remains exactly as confirmed |

**What the customer can reach without the email**, which specification provides it, and **what each
route requires of them.** The word *always* is not used, and the third column is why:

| Route | Specification | What it requires |
|---|---|---|
| the reference on the confirmation page, shown immediately and independently of the email | `P-TKT-03` | a signed-in session, a network, a device |
| the same page, durable and reachable again at `/bookings/{reference}` | `P-TKT-03`, `P-TKT-09` | the same three. `EP-TKT-01` is authenticated and ownership-only; a signed-out visit is `401` |
| the reference in their own bookings list | lane E5's screen, reading the same booking row | the same three. `E5 P-ACC-10` is authenticated |
| a resend they can trigger themselves | `P-TKT-07` | the same three, **plus knowing that the receipt failed** — and nothing tells them (`P-TKT-11`, and the failed state is off the customer API by `P-TKT-09`) |

**All four routes share one precondition, and naming it is the point of the column.** Every one needs
an **authenticated session**. A guest reaches none of them, which is consistent rather than a gap — a
guest cannot book (`SRC-003 OPEN-BOOK-02`) — but **a customer who is signed out at the entrance and
has forgotten their password reaches none of them either**, and that one is not consistent with
anything.

**The route that restores a session is the route that cannot help here.** A password reset writes a
`password_reset.send` row into **the same `outbox_message` table**, relayed by **the same relay**,
consumed by **the same worker**, and sent through **the same SES identity** (`P-TKT-04`, `P-TKT-12`)
that has just failed to deliver the receipt. When SES is the failing component, account recovery fails
with it — and `P-ACC-07`'s deliberately uniform `202` means the customer cannot tell that it did.
**The four routes are not four independent routes; three of them and the fix for the fourth all
terminate at the same session.**

**Nothing is specified against that, and nothing may be.** A second channel, a fallback address, a
one-time link, or any unauthenticated route to a reference is a product answer to a post-capture send
failure, which is exactly `OPEN-EMAILFAIL-01` (`FR-ADR-049`). The shared dependency is recorded in the
table it belongs to rather than discovered at a door.

**What is deliberately absent.**
- No message, banner, email, or page state for a definitively failed send.
- No change to the booking's validity, because whether it stays valid is part of the reserved question
  (`FR-ADR-049` dimension 1).
- No refund path of any kind. There are no refunds (`SRC-003 OPEN-CANCEL-01`, `FR-ADR-013`), and a
  refund invented for this case would be a money decision made by a model.
- No automatic second channel. There is no phone number and no second address on an account.
- No bounce or complaint handling. SES publishes both to SNS and nothing subscribes (`FR-ADR-060`).
  Marking an address invalid is a product behaviour affecting a customer's ability to receive their
  ticket, and that is exactly what is reserved.

**Phase 5 ships the mechanism and not the message.** The outbox, the claim, the retries, the dead
letter path, the on-screen reference and the resend are all buildable, all correct, and all
independent of the answer. Only the customer-facing message and the booking's disposition wait
(`FR-ADR-049`).

**The five dimensions an answer has to cover** are enumerated in `FR-ADR-049` and are not restated
here, because restating them in a PRD invites someone to answer them in a PRD.

### `P-TKT-11` · Nobody is watching a receipt that fails · `RULED`
`[SRC: SRC-003 OPEN-OPS-01 · SRC-002 §8.5.2 · SRC-002 §6.3.6 · FR-ADR-068 · FR-ADR-032 · FR-ADR-059 · FR-ADR-057]`
`[BRD: R-TKT-02 · R-TKT-06]`

**Behaviour.** Exactly one alarm is ruled for this system, on the ECS service's running task count
below 1 (`SRC-003 OPEN-OPS-01`, `FR-ADR-068`). **Dead letter queue depth is not alarmed. Neither is
`outbox_message` pending count, nor the SES bounce and complaint rate.** A receipt that fails
repeatedly is therefore invisible until a person looks at the table.

**Who may do it.** Nobody. This specification describes an absence and the absence is deliberate:
alarms are Zone C (`SRC-002 §6.3.6`), the client ruled one alarm, and building five more would be both
writing Zone C and inventing scope.

**Preconditions.** None.

**Happy path.** There is none. This specification exists so the gap is written down rather than
discovered.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | A receipt fails past `maxReceiveCount` and lands in the dead letter queue | the message sits there. `receipt_dispatch.status` is `failed` with the SES error | **nothing.** No email to the operator, no banner, no entry in any screen that exists in v1 |
| 2 | The outbox relay is stuck and `pending` rows accumulate | the rows accumulate | nothing |
| 3 | SES **accepts** every receipt for a whole evening and every one **bounces afterwards** | every send is recorded as **`sent`**, because acceptance is what `P-TKT-05` records and a bounce arrives later and separately. The bounce notifications publish to SNS and nothing subscribes (`FR-ADR-060`) | **nothing — and this is worse than row 1.** Row 1 at least leaves a `failed` row. Here the product's own record says the receipts went out |
| 3a | SES **refuses** every receipt at the call — a sandbox refusal, a suspended identity, an unverified sender | every send is recorded as `failed` with the SES error, and each message ends in the dead letter queue as row 1 | nothing |

**Server-side validation.** Not applicable.

**What is available to a person who does look.** `/metrics` exposes queue depth
(`SRC-002 §7.7`, `FR-ADR-057`) and **nothing scrapes it** — it is not an alerting mechanism and must
not be counted as one. The other thing available is the `receipt_dispatch` table, and the next block
says what it can and cannot answer. The runbook must name both, **in these terms and not in shorter
ones.**

**`receipt_dispatch` answers a narrower question than its name suggests, and the difference is the
whole of this specification's usefulness.** It records **whether SES accepted the message**, when, and
under which `ses_message_id` — `P-TKT-05` step 5 writes `sent` on acceptance and **nothing ever
revises it afterwards**. It does **not** record delivery. SES publishes bounces and complaints to SNS
and **nothing subscribes** (`FR-ADR-060`, `P-TKT-10`), so a receipt that bounced, or that the
customer's mail provider filed as spam, sits in this table as `sent` and is **indistinguishable from
one that reached the inbox**. The product's knowledge of the receipt ends at the SES API call.

So an operator answering *"did this customer get their receipt"* can establish only that the message
was handed to SES. **A `sent` row is evidence of dispatch, never of receipt**, and the last hop — the
one the customer is standing in — is not observed anywhere in this product. **This is stated at
length because the short version is the dangerous one**: `sent` read as *delivered* is the reading
that ends a support conversation with a customer who has paid, cannot enter, and has been told the
receipt was sent. **This specification previously carried that short version**, in the words "the
`receipt_dispatch` table answers 'did this customer get their receipt'", which was a claim of
knowledge the product does not have, made in the one row whose subject is what nobody can see.

**Adding bounce handling is not the fix and is not available here.** Subscribing to the SNS topic and
marking an address invalid changes a customer's ability to receive their ticket, which is
`OPEN-EMAILFAIL-01` — `OPEN` and reserved (`FR-ADR-049`, `P-TKT-10`). **The document stops claiming
the knowledge; it does not go and get it.**

**And there is no product action available on a receipt that has failed.** Discovery is one half of an
operator's problem and the other half is missing, so it is written here rather than found at the
moment it is needed. **No endpoint, screen or job in v1 re-sends a receipt on an operator's behalf.**
`EP-TKT-02` is authorised on ownership alone, with **no override for any role** (`P-TKT-07`,
`P-TKT-09`, `EP-TKT-02`'s `authorisation_rule`), so an admin looking at a dead-lettered receipt for a
paying customer **cannot press that customer's resend control for them**. What exists is:

| Route | What it needs | Why it may not be enough |
|---|---|---|
| the customer presses the resend control themselves (`P-TKT-07`) | that they know the receipt failed | **nothing tells them.** The dispatch state is off the customer API (`P-TKT-09`) and `P-TKT-10` writes no message |
| a person redrives the dead letter queue in the AWS console | an operator with console access | **Zone C** (`SRC-002 §6.3.6`), specified in **no file** in `docs/30 Deployment/`, and not a product capability at all |

**No operator resend is specified here and none may be added by whoever builds this.** An
administrative action taken on a customer's booking after a post-capture send failure is the substance
of `OPEN-EMAILFAIL-01` — *what the product does when a paid-for receipt definitively fails* — which is
`OPEN` and reserved to the client (`FR-ADR-049`). Building it would also reverse the ownership-only
rule the merge pass adjudicated across `EP-TKT-01`, `EP-TKT-02` and `P-ACC-12`, and would put a
customer's email address into an admin response (`P-TKT-07`). **The gap is stated, not closed.**

**The recommendation, offered and not adopted.** A CloudWatch alarm on non-empty dead letter queue
depth is the single most valuable thing the client could add, and `FR-ADR-068` carries it as a
recommendation rather than a decision. It is the client's call, not a stricter version of theirs, and
it is not built here.

### `P-TKT-12` · Send the password-reset email exactly once per request · `RULED`
`[SRC: SRC-002 §E E-5 · SRC-002 §8.5.2 · SRC-003 OPEN-EMAIL-01 · FR-ADR-031 · FR-ADR-032 · FR-ADR-050 · FR-ADR-059 · FR-ADR-060]`
`[BRD: R-ACC-04 · R-TKT-02]`

**Behaviour.** The worker consumes a `password_reset.send` message, reads the token row it names,
renders the email and sends it through SES. **This is the only credential-bearing message the queue
carries, and it is the sole route back into an account whose address is taken permanently**
(`FR-ADR-012`), so it is specified to the same standard as the receipt rather than left as a branch.

**Who may do it.** The worker process alone. No customer-facing endpoint sends mail directly.

**Preconditions.** The message carries `user_id`, `reset_token_id`, `request_id`, `message_version`
(`P-TKT-04`). **The token itself is never in the queue** — it is a credential, and the worker reads
what it needs from the row.

**Happy path.**
1. Read the `password_reset_token` row by `reset_token_id`.
2. **Claim it**, by the same mechanism the receipt uses and for the same reason — SQS is at-least-once
   and the outbox relay can re-send. The claim is a conditional update on the token row itself, and it
   carries the **stale branch** exactly as `P-TKT-05`'s receipt claim does:

   ```sql
   UPDATE password_reset_token
      SET email_claimed_at = :now
    WHERE id = :reset_token_id
      AND email_sent_at IS NULL
      AND (email_claimed_at IS NULL
           OR email_claimed_at < now() - :stale_interval)
   RETURNING id
   ```

   where `:stale_interval` is `RECEIPT_CLAIM_STALE_SECONDS`. **Affecting zero rows means one of two
   things — the email has already been sent, or another delivery is running right now** — and in both
   the worker deletes the message and stops. No second email.
3. Render the email and send it through SES **under `SES_SEND_TIMEOUT_MS`**, for the reason
   `P-TKT-05` gives: it is the same worker and the same port, and an unbounded call here holds
   `email_claimed_at` live so that no redelivery can retake the job until
   `RECEIPT_CLAIM_STALE_SECONDS` has elapsed — on the one message a locked-out account depends on.
4. On success, record the send and delete the queue message:
   `UPDATE password_reset_token SET email_sent_at = :now WHERE id = :reset_token_id`.

**Two columns, because one cannot answer both questions.** `email_claimed_at` says *a worker is
holding this job*; `email_sent_at` says *an email went out*. `P-ACC-07` step 5 carries both on the row.

**The correction this row previously needed, stated rather than quietly applied.** The published
statement was
`UPDATE password_reset_token SET email_sent_at = :now WHERE id = :id AND email_sent_at IS NULL`,
against an exception row asserting that a stale claim is released by an age threshold. **The SQL could
not express that and the two could not both be true.** Implemented verbatim, a worker that died
between the claim and the send left `email_sent_at` set with no email sent; every redelivery then
affected zero rows, was read as "already sent", and was deleted. **No reset link would ever be sent,
nothing would be logged as a failure, and `P-ACC-07`'s deliberately identical `202` means the customer
cannot tell.** On a product where an address is taken permanently (`FR-ADR-012`), where there is no
support desk and where this is the only route back into an account, that is the account gone. The
receipt's own claim had the stale branch and the credential-bearing twin did not.

**One reclaim mechanism, stated once, because this row previously implied three.** The claim is
`email_claimed_at` and **it is released in exactly two ways, which are one mechanism and not two**: a
worker that fails and is alive to know it clears the column immediately (exception 4), and a worker
that dies before it can clear anything is overtaken by the age branch in the `WHERE` clause above
(exception 6). The first is the fast path of the second and neither is a separate rule.
**`email_sent_at` is not a claim.** It is the terminal record of a send, it is set only after SES
accepts, and **it is never cleared by anything** — which is what makes a duplicate credential email
impossible even if the queue delete fails and the message redelivers a day later.

**What the claim does with every state it can find.** Stated exhaustively, as `P-TKT-05`'s does, so a
reader can tell a first delivery from a reclaim without deriving it from the `WHERE` clause.

| Row state found | What the claim does |
|---|---|
| `email_claimed_at IS NULL`, `email_sent_at IS NULL` | **Claims it.** The ordinary first delivery |
| `email_claimed_at` newer than `RECEIPT_CLAIM_STALE_SECONDS`, `email_sent_at IS NULL` | Nothing. Another delivery is running. Zero rows, the message is deleted, one `INFO` line |
| `email_claimed_at` older than `RECEIPT_CLAIM_STALE_SECONDS`, `email_sent_at IS NULL` | **Reclaims it.** The previous worker died mid-send. This is the branch whose absence was the defect |
| `email_sent_at` set | Nothing, whatever `email_claimed_at` holds. The email went out. Zero rows, the message is deleted |
| no row at all | Zero rows. Exception 1: deleted and logged at `WARNING` |

**Why the token row is the claim rather than a second table.** It already exists, it is already unique
per request, and it already has the right lifetime — the row is the thing the email is about. A
`receipt_dispatch`-shaped table keyed on `booking_id` cannot hold this job at all.

**Exception paths.**

| # | Trigger | Server | What the user sees, verbatim |
|---|---|---|---|
| 1 | The token row does not exist | the message is deleted, not retried — nothing will ever make it valid — and the deletion is logged at `WARNING` with the `request_id` | *(nothing — the customer already saw the identical `202` from `EP-ACC-05`)* |
| 2 | The token is already used or past its lifetime | as row 1. **A reset link is never re-sent for a spent token** | *(nothing)* |
| 3 | `email_sent_at` is already set | a duplicate delivery. Zero rows, the message is deleted and nothing is sent. **This holds forever** — `email_sent_at` is never cleared, so a redelivery arriving a day after a failed queue delete still sends nothing | *(nothing)* |
| 3a | `email_claimed_at` is set and newer than `RECEIPT_CLAIM_STALE_SECONDS`, `email_sent_at` null | another delivery is running this job now. Zero rows, the message is deleted, one `INFO` line | *(nothing)* |
| 4 | SES refuses the send, **or the call does not answer within `SES_SEND_TIMEOUT_MS`** | the claim is **released explicitly** — `UPDATE password_reset_token SET email_claimed_at = NULL WHERE id = :id AND email_sent_at IS NULL` — the message is **not** deleted, and SQS redelivers, which the next delivery claims immediately rather than waiting out the age threshold. **This is the fast path of the one reclaim mechanism, not a second one**; `email_sent_at` is untouched because on a refusal nothing was sent. **On a timeout the outcome is unknown**, exactly as in `P-TKT-05`, so the retry may deliver a second copy — which is harmless here in a way it is not for a receipt, because both copies carry the **same single-use token** and are therefore the same link rather than a second one (`P-ACC-07`) | *(nothing on screen — the customer is not on the site)* |
| 5 | The send fails `maxReceiveCount` times | the message reaches the dead letter queue, and **nothing watches it** (`S7.14`). The customer asked for a reset link and never receives one, and no one is told | *(nothing — this is the account-recovery twin of `OPEN-EMAILFAIL-01`, and it is stated rather than hidden)* |
| 6 | The worker dies between the claim and the send | `email_claimed_at` is set, `email_sent_at` is **null**, and no email went out. Nothing survives to release the claim, so the age branch in the claim's own `WHERE` clause does it: after `RECEIPT_CLAIM_STALE_SECONDS` the next redelivery reclaims the row and sends. **This is the case the previous statement could not express**, and it is the one that lost accounts | *(nothing — the link simply arrives late)* |

**Server-side validation.** `reset_token_id`: integer, positive, existing. `user_id`: must match the
token row's owner — a mismatch is a defect in the producer and the message is dead-lettered, not sent.

**What the email carries.** The customer's address as the recipient; a subject naming the product and
the action; one sentence saying a reset was requested; the link, carrying the token; the expiry in
minutes, **interpolated from `PASSWORD_RESET_TTL_SECONDS / 60` and never typed** (`P-ACC-07`); and one
sentence saying that if they did not ask for it, nothing has happened to their account and they need
do nothing. **It carries no booking data, no reference and no personal detail beyond the address it is
sent to.**

**Phase.** 5, with the receipt — they are the same worker and the same port.

**Worked example 1 — a duplicate delivery. One email, which is the property that must not regress.**

```
10:00:00Z  EP-ACC-05 accepts a reset request, writes token 88, enqueues password_reset.send
           email_claimed_at = NULL   email_sent_at = NULL
10:00:01Z  worker delivery 1: claim -> 1 row.  email_claimed_at = 10:00:01Z
           SES accepts.  email_sent_at = 10:00:02Z.  message deleted.  ONE email sent.
10:02:00Z  SQS redelivers the same message (at-least-once)
           worker delivery 2: claim -> 0 rows, because email_sent_at IS NOT NULL
           message deleted, nothing sent.  STILL one email.
```

**Worked example 2 — the crash, which is the case the old statement got wrong.** Take
`RECEIPT_CLAIM_STALE_SECONDS = 900` against a visibility timeout of 120 seconds, the same pair
`P-TKT-05` works through.

```
10:00:00Z  worker delivery 1: claim -> 1 row.  email_claimed_at = 10:00:00Z
10:00:01Z  the container is killed before the SES call.
           email_claimed_at = 10:00:00Z   email_sent_at = NULL   NO email sent.

           UNDER THE OLD STATEMENT
             every redelivery: WHERE email_sent_at IS NULL -> 0 rows  (it was NOT null)
             read as "already sent", message deleted, nothing logged as a failure.
             The customer never receives a link and the account is unrecoverable.

           UNDER THIS STATEMENT
10:02:00Z  redelivery: claim age 120 s, not > 900 -> 0 rows, message deleted, INFO
             ... seven further redeliveries, each 120 s apart, each the same
10:16:00Z  redelivery: claim age 960 s > 900 -> 1 row. RECLAIMED.
           email_claimed_at = 10:16:00Z, SES accepts, email_sent_at set. ONE email sent, late.
```

**The link arrives about sixteen minutes late rather than never**, and the same two caveats
`P-TKT-05` records against these numbers apply here unchanged, because it is the same variable: the
threshold must exceed the visibility timeout or a redelivery would reclaim a live claim and send a
second credential email, and eight redeliveries are spent before the reclaim, so a `maxReceiveCount`
of eight or fewer sends the message to the dead letter queue first and the link is never sent
(`FR-ADR-059`, and both are Zone C values the client sets). *(reasoned from the configured values,
not observed.)*

**The guard is the conditional update, not the queue's configuration** — `maxReceiveCount` and the
visibility timeout are Zone C values the application cannot see (`FR-ADR-032`).

### Article X candidates raised by this lane

**No new reserved question. One new `PROPOSED-` row, and it is not reserved** —
`PROPOSED-REFCHAR-01`, below the table. Every **reserved** question this lane touches maps onto an
Article X row that already exists:

| Question this lane hit | Existing row |
|---|---|
| What a customer is told when the receipt definitively fails, whether the booking stays valid, **and what an operator may do about one** — no admin resend exists and none is specified (`P-TKT-11`) | `OPEN-EMAILFAIL-01` (`FR-ADR-049`) — carried as `P-TKT-10`, written as `OPEN` |
| Whether the receipt may carry a poster or any supplied image | `OPEN-ATTRIB-01` (`FR-ADR-007`) — resolved conservatively: **no image in the email at all** |
| Whether the link in the receipt reaches the site over TLS | `OPEN-TLS-01` (`FR-ADR-069`) — the link reads `PUBLIC_BASE_URL` from configuration and this lane asserts nothing about the scheme. `FR-ADR-060` records that deliverability without a verified domain is materially worse, which is a second argument for closing this row and a different one from TLS itself |
| What happens to a receipt when an admin withdraws a showtime that has bookings | `OPEN-SHOWCANCEL-01` (`FR-ADR-023`) — no withdraw capability exists in v1, so this lane specifies nothing for it |

**`PROPOSED-REFCHAR-01` — should the booking reference carry a check character, and should the
alphabet drop `2`/`Z`, `5`/`S`, `8`/`B` and `6`/`G`?** Class: **product**. Not reserved, and **not
raised because the build session may not decide it** — `SRC-003 OPEN-TICKET-01` rules the exclusions
and then says *"Format specified in the PRD"*, so the format is this document's to set and adopting a
narrower alphabet would be the stricter option, needing no signature (`CONSTITUTION.md` Art III.10).

It is raised rather than decided for two reasons, and the second is the one with a date on it.

1. **It is a larger decision than the gap it closes.** A check character changes the length and
   therefore the `FR-XXXX-XXXX` presentation form, the copy control, the accessible name that spells
   the characters, `SCR-TKT-02`'s subject and body, and both endpoints' `reference` parameter — and
   it only detects a mis-read, it does not correct one, so `P-TKT-02` still refuses to guess. A
   narrower alphabet fixes the four *visual* pairs and does nothing at all about the spoken set
   (`B` `C` `D` `E` `G` `P` `T` `V` `Z` `3`, `M`/`N`, `F`/`S`), which is the half that bites at a door.
   Neither is a small change and neither is a complete fix; choosing between them is a product
   decision the client should see.
2. **It stops being decidable at Phase 4.** A reference already issued to a customer cannot be
   re-cut, and there are no refunds and no reissue path (`SRC-003 OPEN-CANCEL-01`). The change is free
   while no booking exists and impossible once the first one is confirmed — **the same deadline shape
   as `OPEN-SEATLABEL-01`, on a different mechanism** (`P-TKT-01`). If the client is to rule it, they
   must be asked **before the first confirmed booking**, not when somebody notices at a door.

**Ruled by `SRC-004 R-5` (2026-10-18), before the first confirmed booking:** both — the alphabet
drops `Z S B G` and the 8th character is a check character, with the length kept at 8 so the
presentation form is unchanged. `P-TKT-01` carries the ruled format.

### Durations this section publishes, checked against **both halves** of `S7.20`

`S7.20` owns the rule and this section owns none of it. It has **two halves, and a string has to
satisfy both**:

1. **Derivation.** `Retry-After = ceil(window_seconds / capacity)` — the time to earn one token from
   empty — taken from **whichever bucket refused**. It is not the bucket's capacity and it is not its
   window. Where two limiters guard one endpoint, a row publishing one figure **must name its bucket**.
2. **Rendering.** `"<n> seconds"` below 120; `"<m> minutes"` with `m = ceil(seconds / 60)` at 120 and
   above; singular at 1.

**The first audit of this section checked only the second half, and that is how a wrong number
survived it.** Both halves are checked below, and the derivation column is the one that matters,

| `"Try again in 45 seconds."` — `P-TKT-02` exception 6 | **3 seconds** (per user) and **1 second** (per IP), as two rows naming their buckets | `45` is derived from nothing: not a refill interval, not a capacity, not a window, of either bucket on the endpoint. It rendered correctly, which is exactly why a threshold-only audit passed it. `P-ACC-12` publishes the correct 3 for the same buckets, so this section was disagreeing with its own sibling |
| One row 5 triggered by "the per-booking **or** per-user bucket", publishing only `"in 4 minutes"` | rows **5** and **5a**, one per limiter | The two produce 240 and 3 — three orders of magnitude apart. A single row told an engineer to render the per-booking figure when the per-user bucket refused |

Every other occurrence of *seconds* or *minutes* in this section is arithmetic in a worked example — a
120-second visibility timeout, a 900-second stale threshold, a 30-second relay age — and not a string
a customer reads. `S7.20` governs published `Retry-After` copy, so those are outside both halves.

### Where I would have had to guess and did not

**1. What the durable confirmation page says after a definitive send failure.** `FR-ADR-048` gives the
copy for the first render. On a later visit the sentence "a receipt is on its way" may be false, and
`OPEN-EMAILFAIL-01` reserves the replacement. **I wrote no replacement sentence.** The page renders no
email-status line at all on a later visit. Omission closes no question; a sentence would. This is the
single place in the lane where the specification is deliberately silent about something a developer
will notice, and it must not be filled in by whoever builds `SCR-TKT-01`.

**1a. Whether the later-visit state should name the receipt's address, now that a reload lands there.**
`P-TKT-03` decides *which* state renders and states the consequence: a customer who reloads within
seconds loses the sentence naming the address. The obvious follow-on — put the address on the
later-visit state too — **was considered and refused, and no `PROPOSED-` row was raised for it**, for
two reasons that are worth writing down rather than leaving as a silence. First, any standing statement
on that page about where a receipt is or is not going is the substance of `OPEN-EMAILFAIL-01`: on a
later visit the send may already have definitively failed, so a line naming the address would assert
something the system does not know, which is the failure mode that row exists to prevent. Second, the
customer is not left holding nothing — the reference is in the reference block in **both** states, and
it is the proof of purchase and the way into the hall (`FR-ADR-048`); the address is also returned by
`EP-TKT-02`'s `202` body when they press the resend control, which is present in both states. **A
`PROPOSED-` row is for a question that must be answered before the product is right. This one is
already answered, by an open row that must not be pre-empted.**

**2. Whether the receipt's dispatch state appears on the customer API.** No source answers it. Putting
`receipt_status` in `EP-TKT-01`'s response forces the interface to render something for `failed`, which
is the reserved question. I left it off the customer API entirely and said so in `P-TKT-09`, rather
than adding a field and leaving the rendering to a later session.

**3. Whether a bounced address should be marked invalid.** `FR-ADR-060` records that SES publishes
bounces to SNS and nothing subscribes. Marking an address invalid changes a customer's ability to
receive their ticket, which is `OPEN-EMAILFAIL-01`. **No bounce handling is specified.**

**4. Whether a person at the door should be given anything.** `SRC-003 OPEN-TICKET-02` rules a manual
human check. It does not say what the venue's process is — a printed list, a laptop, a phone. That is a
business process, not software, and I specified no door screen, no staff account and no lookup that a
door attendant could use. `EP-TKT-01` is authenticated and returns only the caller's own booking
precisely so it cannot quietly become the door tool.

**4a. Whether the reference should carry a check character, or a narrower alphabet.** The format is
the PRD's to set (`SRC-003 OPEN-TICKET-01`: *"Format specified in the PRD"*), so this is not a
question I was forbidden to answer — it is one I judged larger than the defect that exposed it and
**time-limited in a way the client has to be told about before Phase 4.** Raised as
`PROPOSED-REFCHAR-01`. What I did do is stop `P-TKT-01` implying that the exclusion list made the
reference unambiguous, which it does not. *(Since ruled by `SRC-004 R-5`; `P-TKT-01` carries it.)*

**4b. What an operator does about a receipt that has definitively failed.** No admin resend endpoint
was added, no dead-letter redrive was specified, and no bounce subscription was designed. All three
are the product acting on a post-capture send failure, which is `OPEN-EMAILFAIL-01`. `P-TKT-11` now
says the operator has nothing to act with, and stops there.

**5. The value of the per-booking resend interval, the claim-stale threshold and the relay
threshold.** Every one of these is a number no source states. Each is a named configuration value with
an `ASSUMED` starting figure, flagged above, rather than a literal in the code.

**6. What happens to a receipt for a booking on a withdrawn showtime.** `OPEN-SHOWCANCEL-01` is open
and no withdraw capability exists in v1, so there is no path to specify. I did not specify one
speculatively.

### Contradictions found against a frozen source, an ADR, or the BRD

**1. `FR-ADR-032` against `FR-ADR-048` — the resend and the claim row.** `FR-ADR-032` says the
`receipt_dispatch` row is unique on `booking_id` and that "a `sending` or `sent` claim is not"
retryable. `FR-ADR-048` says there is "a resend control on the customer's booking page, which
re-enqueues the receipt job". Read literally together, a resend after a successful send can never
produce a second email, so the control does nothing. Both records are `APPROVED` and immutable, so
neither is re-opened: `P-TKT-07` reconciles them with `dispatch_seq`, described above and flagged for
the merge pass. **Named here rather than resolved silently, because a reader of either ADR alone will
reach a different implementation.**

**2. `FR-ADR-059` against this lane's payload, on both topics.** `FR-ADR-059` fixes the queue payload at
`booking_id`, `request_id` and `message_version`, and says "no customer data travels in the queue".
Two departures, both flagged rather than assumed:

- **`dispatch_seq` on `receipt.send`.** It is job state, not customer data, so the rule's purpose is
  intact — but `FR-ADR-059`'s enumeration is exhaustive as written and this is a fourth key.
- **A second topic, `password_reset.send`, with the payload `user_id`, `reset_token_id`, `request_id`,
  `message_version`** (`P-TKT-04`). `FR-ADR-059`'s enumeration describes the receipt message and the
  account lane's reset email uses the same outbox, the same relay and the same worker. **Adjudicated in
  the merge pass**, because the alternative was a reset email that cannot be enqueued, cannot say which
  reset it is for, and would have been deleted by `P-TKT-05`'s booking check — breaking the only route
  back into a locked-out account. `FR-ADR-059`'s actual rule is honoured rather than bent: the payload
  carries `reset_token_id`, an identity, and **never the token**, exactly as `receipt.send` carries
  `booking_id` and never the email address. **`06 DataModel` and the account lane must confirm both key
  sets.**

**3. `FR-ADR-052`'s registry has no not-found code**, while `FR-ADR-015` requires that a mistyped
reference "simply fails". Emitted as a `newerrorcode` block rather than resolved inline.

**3a. `EP-TKT-01`'s ban on an admin override against `EP-TKT-02`'s — resolved, and recorded so it is
not re-opened.** The merge pass ruled that **no admin may read another customer's booking**
(`P-TKT-09`, `EP-TKT-01`, agreeing with `P-ACC-12`). **The same rule now holds on the resend**:
`P-TKT-07`'s *Who may do it* and `EP-TKT-02`'s `authorisation_rule` both state that no role is exempt
and that there is no override. Two arguments decided it, and both are recorded in `P-TKT-07`:

- `EP-TKT-02` resolves its `reference` path parameter through `P-TKT-02`, whose rule returns 404 for "a
  well-formed reference belonging to another customer". Under `EP-TKT-01`'s rule that 404 applies to an
  admin as well, so an admin cannot resolve another customer's reference at all — an override would
  have been **unreachable**, not merely unused.
- `EP-TKT-02`'s `202` body carries `email_address`. An admin resend on somebody else's booking would
  disclose that customer's email address, making the endpoint a read of a customer record by another
  route — the exact thing `EP-TKT-01` refuses.

**Adopting ownership-only everywhere is the stricter reading and needs no signature**
(`CONSTITUTION.md` Art III.10); granting the override would have been inventing a privilege no frozen
source or `APPROVED` record grants. `FR-ADR-048`'s resend control is not withdrawn — it still exists,
for the booking's owner, which is who `FR-ADR-048` describes pressing it. **No claim that `EP-TKT-02`
carries an admin override survives anywhere in this section**; it was a stale sentence, and it is
deleted rather than reconciled.

**4. `SRC-002 §8.5.1` still reads "generates the ticket QR code" in the frozen text**, corrected by
`SRC-002 §E E-5`. Not a defect — the erratum governs — but it is recorded because a session reading
`§8.5.1` alone will build a QR code. The same applies to `SRC-001 §5.3.3`'s "scannable ticket",
corrected by `SRC-001 §E E-9`. **No QR code is generated anywhere in this lane.**

**4a. `FR-ADR-032`'s "a duplicate receipt is impossible" has one case it cannot cover, and it is named
rather than left implied.** The claim makes two *senders* impossible. It cannot make two *sends*
impossible when a send's outcome was never returned — a `SendEmail` call abandoned at
`SES_SEND_TIMEOUT_MS` may or may not have been accepted, and the retry that follows may deliver a
second identical receipt (`P-TKT-05`). The record is not re-opened and the mechanism is not changed:
the alternative to retrying an unknown outcome is a customer who has paid and gets nothing, which is
the worse failure on this product's own terms. **Recorded here because a reader of `FR-ADR-032` alone
will believe the guarantee is unconditional.**

**5. `CONSTITUTION.md` Art I.6 still names "a booking reference and a scannable ticket" in the win
condition.** Already recorded as stale by BRD `B1.5` and `lens-merge.md §4`, and not re-litigated here.
The corrected win condition is BRD `B3.3`.

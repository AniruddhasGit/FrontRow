Every failure this product can produce has a **stable machine-readable code**. The interface
branches on the code and never on the message text, which is a presentation string that will be
edited (`FR-ADR-052`).

## The envelope

```json
{
  "error": {
    "code": "SEAT_UNAVAILABLE",
    "message": "Seats C12 and C13 were taken by another customer.",
    "details": {
      "unavailable_seats": [
        "C12",
        "C13"
      ]
    },
    "request_id": "a1b2c3d4"
  }
}
```

`request_id` is present on **every** error response and is **shown to the customer on 5xx only**.
On a 4xx the customer can act on the message themselves and an opaque id is noise.

## Wording rules — `SRC-002 §2.2`

1. **Say what happened, not how it felt.**
2. **Say what to do next** where there is something to do.
3. **Never blame the customer for a race they lost.** Losing a seat is the system working correctly.
4. **Nothing internal leaks** — no stack trace, no SQL, no exception class, no hostname, no table name.

## Codes raised by a handler and not by any endpoint

These are **not** unused. They are decided before a route is chosen, so no endpoint block
can list them and none does — the empty `Raised by` above is the correct state for them,
not a gap.

- `METHOD_NOT_ALLOWED` — raised by the application's method-not-allowed handler, which runs before any route is selected (`P-XCT-11`)

across all forty-nine losers (`FR-ADR-034`).

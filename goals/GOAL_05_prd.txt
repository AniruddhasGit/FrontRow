DELIVERABLES - the PRD, with these sections
  S1  Reading rules and provenance grammar.
  S2  Scope carried from the frozen BRD.
  S3  Personas, roles, and the full surface/route inventory.
  S4  Product specifications by epic, ID'd P-xxx-nn, each carrying: behaviour, the [SRC:] tag,
      its BRD row, preconditions, the happy path, EVERY exception path, server-side validation,
      the exact error the user sees, and who may do it.
  S5  UX specification - binding to docs/05 B DesignSystem by token name. Every screen: fields,
      actions, states (empty/loading/error/success/partial), and what the user leaves with.
  S6  The API contract - every endpoint: method, path, request shape, response shape, status
      codes, idempotency behaviour, and the authorisation rule that applies.
  S7  Cross-cutting floors - concurrency, money, audit, rate limits, sessions, caching, health.

RULES FOR THE CONTENT
  - Every P-row carries a [SRC:] tag AND names the BRD row it satisfies.
  - Every rule that computes a number states the rule, its inputs, and a WORKED EXAMPLE with the
    expected answer. This is what makes an acceptance criterion binary later. At minimum:
    the price of a named multi-seat selection with its seat categories and any tax, and the exact
    moment a hold expires given a named start instant.
  - THE SEAT LIFECYCLE IS A STATE MACHINE AND IT IS SPECIFIED HERE, exhaustively: available ->
    held-by-me -> held-by-me-and-paying -> sold, plus every failure edge (hold expires during
    payment, payment fails after hold expired, someone else takes the seat between map render
    and hold request, the browser closes mid-checkout, the container is killed mid-confirm).
    Every edge names what the customer is told, in the exact words they see.
  - Error behaviour is specified, never left to the implementer. Every error has a stable code.
  - "TBD" is not a value. An unsettled question is an Art X row.
